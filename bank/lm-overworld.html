The overworld: how SMW stores it and how Lunar Magic edits it

Addresses are vanilla and traced in the SMW disassembly's bank 04 unless a section says otherwise. Lunar Magic facts come from LM's help on the overworld editor [LM-DOC], restated in plain words, and from controlled before/after saves in LM and several LM-edited ROMs compared against vanilla.

1. Geometry

Two maps, each 32x32 16x16 tiles (512x512 px). The main map is index 0x000-0x3FF. The six submaps share one second map, index 0x400-0x7FF, two columns by three rows; a "submap" ($1F11: 1 Yoshi's Island, 2 Vanilla Dome, 3 Forest, 4 Valley, 5 Special, 6 Star) is a fixed camera plus a palette, not separate storage. Cameras at $049A0C: 1 (-17,-40), 2 (-17,128), 3 (-17,296), 4 (240,-40), 5 (240,128), 6 (240,296) px.

Lunar Magic draws both on one canvas: the main map at tile Y 0-0x1F, the submap map at Y 0x20-0x3F, with the submap map rotated 16px right and 8px down (two 8x8 cells and one row). Its tilemap's last two columns and last row wrap round to the lower map's left edge and top, as a hardware scroll would show them, and layer 1 rides the same shift. The game itself shows both layers on the plain grid; the rotation is only LM's canvas layout [MEASURED, aligning LM's window and an emulator frame of the game against a raw render].

Layer 1 index ($049885): (X&0xF) | (X&0x10)<<4 | (Y&0xF)<<4 | (Y&0x10 ? 0x200 : 0), i.e. four 16x16-tile screens TL TR BL BR of 0x100 each, +0x400 on the submap map.

2. Layer 1: level tiles, clouds, Mario's paths (16x16)

  • Tilemap $0CF7DF, 0x800 bytes, one tile number per cell; copied to $7EC800 ($04DC5A).
  • Map16 definitions $05D000, 8 bytes per tile = four words TL, BL, TR, BR; 0xC1 tiles ($05D608 is the next table). Words are standard vhopppcc tttttttt. LM expands this to two pages (0x200 tiles).
  • Tile meaning ($049140, $0492F2): 0 empty; < 0x56 path tiles (walk/climb/swim/exit, 0x4E-0x50 fish, 0x49-0x4B Koopa-kid triggers); 0x56-0x86 level tiles; 0x5F star, 0x5B pipe, 0x82 pipe ignoring directions, 0x81 destroyed castle. Tiles >= 0x81 are not enterable.
  • Vanilla stores no per-tile level number. $04D7F2 scans $7EC800[0..0x7FF] in index order and numbers every 0x56-0x80 tile 1, 2, 3... (translevel). Level = translevel below 0x25, else translevel - 0x24 | 0x100 ($05D88B). LM's "level number to use for this tile" replaces that scan with a per-tile table; §11 has where it lives.

3. Layer 2: the land (8x8)

Two RLE streams: tile numbers $04A533, property bytes $04C02B (decoded at $04DABA). Header byte n: bit 7 clear = copy n+1 literal bytes, set = repeat the next byte (n&0x7F)+1 times; each stream fills one byte of every word until 0x2000 words. The result is two 64x64 8x8 tilemaps in SNES screen order (four 32x32 screens of 0x400 words, TL TR BL BR), main map then submap map, DMA'd to VRAM $3000. Layer 2 scrolls with layer 1 (no parallax); layer 3 is the static border.

Layer-2 event tiles (LM's 6x6 and 2x2 "pieces"): tile bytes $0C8000 (0x900 bytes of 6x6 pieces, then 2x2), property bytes RLE at $0C8D00 in the same encoding as layer 2's streams, so the two bytes join into an 8x8 word. 0xD00 cells in all: 64 pieces of 6x6, then 256 of 2x2. A step writes piece src at dst ($04E4D0 for 2x2 if src >= 0x900, $04E520 for 6x6).

4. Graphics and palettes

  • Tileset row $1931 = 0x11 + submap selects ObjectGfxList $00A92B rows 0x11-0x17 = GFX1C 1D 08 1E on every submap in vanilla (the rows exist so LM can bypass per submap). Sprite set 0x11 selects SpriteGfxList $00A8C3 = GFX10 0F 1C 1D. Layer 3 = GFX28-2B.
  • Per-submap GFX (LM's Overworld > Submap GFX) [MEASURED, by installing the hack through that dialog on four copies of one base (one unchanged as the control, one changing submap 1's FG1, one submap 4's FG1, one submap 1's SP1 and AN2) and diffing].
    • The table is the per-level Super-GFX-Bypass table, seven entries longer: submap N is entry 0x200 + N, N = 0 the main map and 1-6 LM's dialog order (Yoshi's Island, Vanilla Dome, Forest of Illusion, Bowser's Valley, Special World, Star Road). LM reallocates the whole table to fit them (a table at $129000 moved to $18B284 on LM's save).
    • A submap's record is byte-for-byte a level's (CONTRACT §7d, §12b): w0 AN2, w1 AN1, w2/w3 = FG6/FG5, w4-w7 = FG4-FG1, w8-w11 = SP4-SP1, w12-w15 = the layer-3 four. So the dialog's FG1-FG6 are the level record's FG1/FG2/BG1/FG3/BG2/BG3, in the same word order, and FG5/FG6 are BG2/BG3, which the dialog greys unless the merge FG1/FG2 into SP3/SP4 option is on. FG7/FG8 exist as dialog controls but are not laid out. 0x7F is skip this slot, the same convention as a level's.
    • There is no enable bit. LM fills all seven records with the values the vanilla lists imply (14 00 7F 00 7F 00 7F 00 1E 00 08 00 1D 00 1C 00 1D 00 1C 00 0F 00 10 00 2B 00 2A 00 29 00 28 00) and leaves w0 bit 15 clear; the loader reads a submap's record unconditionally. Read back both ways: bytes written into a table LM installed appear in LM's dialog (a hand-patched LM save showed FG1 = 0F and SP1 = 0C on the Forest of Illusion), and LM's dialog writes exactly these words.
    • The hooks. Vanilla's STA $20 : SEP #$20 at $00A140 (the last thing before the JSR UploadSpriteGFX at $00A9DA, whose tail at $00AA50 carries the bypass loader) becomes JSL $0FFAB0, and the LDY #$14 : JSL $00BA28 at $00A147 keeps the LDY but has the JSL NOPped, because the record's AN2 slot now supplies that file. LM's stub at $0FFAB0 is STA $20 : TXA : ASL×4 : CLC : ADC #<record low16> : STA $7FC006 : SEP #$20 : LDA #<bank> : STA $7FC008 : LDA #$42 : STA $7FC009 : LDA #$00 : STA $7FC00B : RTL. The submap comes in as X = submap*2 from vanilla's own LDX $0DB3 : LDA $1F11,X : ASL : TAX at $00A12A, the same place LM's overworld ExAnimation setup reads it (EXANIMATION §10), and $7FC009 = #$42 is what tells LM's loader this is the overworld rather than a level (#$41).
    • What makes LM's dialog read it. Two things, and nothing else: LM's layout stamp 4C 4D 03 01 at $0FF15C, and the record address in the two operand fields LM parses the stub for (ADC #imm at $0FFAB0+9/+10, LDA #imm at +18). A ROM carrying the 35-byte stub with a record address in those fields (even with only its closing RTL replaced) and the stamp in place has LM read the seven records, write an edited slot into that table, and install none of its own loader [MEASURED in both directions; LM_PARITY §2 has the experiments and the negatives].
    • Per-submap LAYER 3 GFX (LM's Overworld > Submap Layer 3 GFX/Tilemap Bypass, the Overworld menu's second item: a separate hack with its own dialog and its own per-submap enable checkbox) uses the same records as a level's layer-3 bypass: w0 bit 14 enables, words 15-12 are LG1-LG4 [MEASURED]:
      • LM reads the record. The dialog's submap list labels each submap with its LG values; with word 15 of submap 1's record patched to 0x2B it showed LG1=02B for Yoshi's Island and 028 for the other six. No stamp beyond the one above is needed; the layer-3 dialog reads the same table.
      • LM writes the record. Picking submap 2, ticking "Enable bypass of standard Layer 3 GFX" and choosing 2F for LG1 left the record at w0 = 0x4014 (bit 14 set, AN2 untouched) and w15 = 0x002F.
      • The game honours it: with the bit on and LG1 = 0x2B, the layer-3 VRAM page changed on the map in an emulator.
      • Opening the dialog does not write the file; the save does.
    • Per-submap layer 3 TILEMAP (LT3). The vanilla routine that loads the overworld's layer-3 tilemap ends in LDA #$02 : STA $420B : RTL at $04D73F: it sets VRAM word $3000 and DMAs 0x2000 bytes there from $7F4000, or $7F6000 when $1F11 says the player is on a submap (DMA parameters at $04DAB3 = 01 18 00 40 7F 00 20). Found in the disassembly and confirmed by mutation: changing that source byte moved VRAM $6000-$7FFF on the map, so the routine runs on the path a new game takes and word $3000 really is the overworld's layer-3 tilemap [CONFIRMED]. The record word and its encoding are a level's, because that is what LM writes: w0 bit 13 enables, w1 = file (bits 0-11) | size index (bits 12-13) | destination index (bits 14-15). The one difference is the window base: a level's layer 3 starts at word $5000, the overworld's at $3000. Ticking "Enable bypass of standard Layer 3 tilemap for this submap" in LM and choosing file 28 left the record at w0 = 0x2014, w1 = 0x6028, and LM's overworld save does not touch $04D730-$04D7A0 (checked against a control save) [MEASURED].
  • Animated tiles: VRAM tiles 0x75-0x7F are rebuilt every frame from GFX14 (the file decompressed last, still in $7EAD00) and uploaded by $00A4E3 (0x160 bytes to VRAM word $0750). Three water tiles, GFX14 0x50-0x52 ($048000), are scrolled in RAM every eight frames ($0480E0: 0x75 rows 0-3 a pixel left and 4-7 right, 0x76 a row down, 0x77 both); LM shows them unscrolled. Eight more cycle, eight frames each: GFX14 tile 0x40 + 8k + frame ($048006, one table of 64; $048123 takes the frame from counter bits 3-5, or 4-6 for the two waterfall slots). Lunar Magic shows counter 8-15: slots 2-7 on frame 1, the waterfall on frame 0 [MEASURED against LM's pixels].
  • Plane 3 from the uploader: vanilla's expand-upload ($00AA80) synthesizes a fourth plane as the OR of the other three for GFX1E always and for GFX08 on tilesets 0x11+ ($00AA8C-$00AA94, the $0A = $FF00 filter), so every drawn pixel of those files lands in colours 8-F of its row. The castles, the level stars and the SNES logo are painted for those colours, and the 3bpp files hold indices 1-7 that never show. The two file numbers are operands of those compares; LM's 4bpp mode bakes the plane into its files and points both compares at GFX32.
  • Palette: the overworld load ($00A5BC) runs the ordinary level palette loader LoadPalette first, with whatever header bytes the last level left (a new game arrives with the intro level 0xC7's), then $00AD25 lays the overworld's colours over it:
    • palettes 4-7 colours 1-7 from $00B3D8 + $00ABDF[$00AD1E[submap]] ($00AD1E = {1,0,3,4,3,5,2}, sets of 0x38 bytes; the special-world-passed set at $00B732)
    • palettes 2-7 colours 9-F from $00B528
    • sprite palettes 8-F colours 1-7 from $00B57C
    • palettes 0-1 colours 8-F from $00B5EC

Both layers draw in rows 0-7; what a layer 1 tile from GFX1E or GFX08 shows is colours 8-F of its row (plane 3 above), so rows 0-3 colours 1-7 (the level loader's leftovers) hardly matter, and LM's palette editor shows them black. Path fading borrows rows 0-3 and C-F colours 1-7 during a reveal. LM's Overworld Palette Editor agrees with this derivation row for row on every submap [MEASURED].

  • LM's overworld palettes. LM's editor shows all 256 colours of a submap as editable, and its first overworld palette save makes them so: a JSL over STY $00 : LDA $1931 at $00AD32 with an RTS at $00AD36, so the vanilla loads never run, and a hook that copies one whole 0x200-byte palette per submap over the CGRAM mirror with one MVN: TAX : LDA $1931 : AND #$0F : DEC : CLC : TXY : BPL + : ADC #7 : + XBA : ASL : ADC #table : TAX : LDY #$0703 : LDA #$01FF : PHB : MVN $00,bank : PLB : SEP #$30 : RTL, then LM 00 01, in a RATS block of 0x30. The table is a RATS block of 0x1C00: submaps 0-6, then the same seven once the special world is passed (X still holds the flag $00AD2B read; which flag is the hack's own setting: one LM-edited ROM reads $1F00, vanilla $1EEA). LM's -TransferOverworld from an LM-edited ROM onto a clean one gives a hook byte-identical to the source's bar the table address. LM keeps the hook where it finds it and rewrites its operands, but frees the table and allocates a new one on each save, so nothing may hold the table's address across an LM save [MEASURED].
  • What LM's conversion writes in the table is not the CGRAM the vanilla loads produce, though: it is the overworld's own loads where they write, 0000 everywhere else (the level loader's leftovers, which is why LM's editor shows rows 0-3 colours 0-7 black), and Mario's ten colours from $00B2C8 at 0x86-0x8F (the game uploads the player's palette there every frame regardless). Checked against 33 distinct LM tables: one differs from that rule in 3 of 3584 colours, another in 4, and the rest only in land colours their authors recoloured. -TransferOverworld from a ROM without the table installs nothing, so LM converts only on a palette save [MEASURED].

5. Level tiles

Per translevel (0-0x5F): exit directions $04D678 (bits 7-6 normal, 5-4/3-2/1-0 secret 1-3; 0 up, 1 down, 2 left, 3 right); base event $05D608 ($FF none; secret exit N fires base+N); level name $04A0FC (word giving three string offsets into $049AC5). Flags RAM $1EA2: bit 7 passed, 6 midway, 3-0 directions enabled (LM adds 5 "no entry if passed", 4 "save prompt"); new-game pairs at $009EE0; Mario/Luigi start $009EF0 = submap 1, tile (6,7). Reveal list $04DA1D to $04DA33 (22 pairs); event N reveals the layer-1 cell at $04D85D[N]. No-auto-move levels $04906C (6). Music per submap $048D8A.

6. Paths

Walkability is the layer-1 tile at the next cell (path < 0x56 or level tile) and the direction bit at the level Mario stands on. What a path tile does is its pose byte at $049FEB (read at $0495EF): bit 3 swims (tiles 28-3E, 50), bit 4 climbs (3F-41, the ladders; also sets $1B80 for the ladder speed table $049414), anything else walks; bit 2 only picks Mario's front-facing walk frames. Exit tiles are the ten in $049426 (25, 40, 42-48, 4D). Fish jump on 4E-50, Koopa Kids trigger on 49-4B. Level tiles 56-82 enter; 83-86 stop Mario without entering.

[CONFIRMED] against Lunar Magic's "Layer 1 Mario Paths" view on a ROM whose layer 1 was a grid of every tile 01-86: LM draws exactly those sets as green / blue / rungs / red / X. LM stores no bitmap for these pictures: its exe resources hold the level editor's slope outlines and the message font, not these.

Step vectors $049058; corner tiles $04A03C; per-tile speed and animation $049EA7. Five hardcoded paths ($049078, $04910E, $0490CA, $049086) that LM cannot display, only disable. Layer-1 paths are static; "a path revealed by an event" is a layer-2 change.

7. Events

0x78 events (bitfield $1F02-$1F10; vanilla tables sized 0x70). Layer-2 standard steps: cumulative index $04E35B (event N = steps E35B[N-1]..E35B[N]-1), 4 bytes per step at $04DD8D [src word][dst word], animated one per frame with a sound. Silent steps (layer 1, and layer 2 on other maps): events $04E8E4, flags $04E910 (bit 0 = layer-2 piece), dst $04E93C, tile/piece $04E994 (0x2C each); applied all at once on load. Destroy (castle, switch palace): events $04E5D6 (0x18), offsets $04E5B6, source tiles $04E5A7, replacements $04E5AC/$04E5B1.

8. Transitions

  • Star/pipe warps: 27 entries. Source $048431[i] (word submap<<8 | tileX) and $048467[i] (tileY); destination $04849D[i] (bits 0-8 X px, 9-12 dest submap) and $0484D3[i] (Y px). LM's "destination index" is derived by matching a destination to another entry's source; LM grows the table to 0x100 and reuses it for level "Location teleports". Every destination vanilla stores is the tile's CENTRE (tile*16 + 8), and every source sits on a star or pipe tile: 0x5A, 0x5B, 0x5F or 0x82 [MEASURED against all 27]. The four arrays are butted together ($048431 + 0x36 is $048467), and vanilla fills all 27 entries, so there is no spare slot without relocating them. A source of $FFFF is a free slot, the shape the game's own search walks past.
  • Exit tiles (walk off one map onto another): source $049964/$049966/$049968 (Y px, X px, submap; 5-byte stride, 14 entries), destination $0499AA/$0499AC/$0499AE, arrival tile $0499F0/$0499F1 (tile Y, tile X). The walk at $049A3F compares the source against Mario's own position $1F19/$1F17 and his submap $13C3, then writes the destination into all three plus his tile $1F21/$1F1F. The three tables are contiguous ($049964 + 0x46 is $0499AA, and + 0x46 again is $0499F0).

The position carries the direction. Mario is centred on the axis he is not moving along and a tile short on the one he is, so an entry is a tile AND a way of travelling through it: moving down (x*16+8, y*16), up (x*16+8, y*16+16), right (x*16, y*16+8), left (x*16+16, y*16+8). The same bytes therefore read as "tile 20 walking down" or "tile 21 walking up"; the one of the two that is an exit tile settles it. This is the "side to enter from" LM's link dialog asks for, and the destination is the partner tile written the same way, since the player keeps travelling as he was [CONFIRMED against all 14 vanilla entries; decoding and re-encoding them reproduces the ROM's own bytes].

The map already knows the side: an exit tile is the end of a path, so the player leaves by the side the path does not use, which can be read off the four neighbours. All 13 vanilla entries that sit on an exit tile agree with it (the fourteenth, entry 04, sits on a plain walk tile). A tile with other than exactly one walkable neighbour is ambiguous.

  • Koopa teleports: three positions $048E49 (X) / $048E4F (Y), triggered by tiles 0x49-0x4B.

9. Sprites

13 slots x 5 bytes at $04F625: type, X lo/hi, Y lo/hi. Types in LM's list order (Lakitu, bird, fish x3, piranha, cloud, Koopa kid x3, smoke x2, sign, Bowser, ghost x2). Mario's and Luigi's start positions are edited as sprites in LM.

10. Lunar Magic's editor

One canvas; left click selects, right click pastes, Ctrl+Right always pastes the selector's tile, left-drag lassos, dragging a selection moves it, Ctrl+Left on a selection edge resizes it as a repeating pattern. Five edit modes:

  • Layer 2 8x8 Editor (the default), and the only mode that shows the two areas beside the maps: the event pieces to the right of the main map, and layer 1's Map16 tiles below the submaps (§10a).
  • Layer 1 16x16 Editor: level tiles AND the invisible path tiles are dragged like any tile; Alt+Right = Modify Level Tile Settings (§11); Alt+Left on two star/pipe/exit tiles links them.
  • Layer 2 Event Editor: Page Up/Down changes event, Home/End step; Shift+Right pastes a silent step.
  • Layer 1 Event Editor: silent steps only, for other submaps.
  • Sprite Editor: 8px steps, Mario/Luigi start.

View toggles: Layer 1, Layer 2, Sprites, Show Level Numbers, Show Event Numbers, Show Star/Pipe/Location Numbers, Show Exit Path Numbers, Layer 1 Mario Paths (green walk, black climb, blue swim, red exit), Future Layer 1 Tiles, Tile Grid, Special World Passed Palette. "Modify Level Tile Settings" holds: level number, base event, direction per exit, reveal-on-events, and the eight initial flags. Gotchas LM warns about [LM-DOC]: test on a fresh save slot (directions live in SRAM); never reuse a level number on two tiles; paths must not dead-end, gap or cross; one destroy and one reveal per event; star/pipe at X=0 on the submap map do not work.

The filler. A cell no table reaches gets LM's filler tile rather than a hole: 8x8 tile 0x7A, a black cross on blue, in palette row 5 (LM's status bar reports "7A" out there, and 0x7A's pixels are colours 1 and 4, which row 5 paints black on the sea's blue). 0x7A is one of the cycling animated slots (0x78-0x7F, §4), so on the map it shows whichever GFX14 frame is up.

LM paints that same X over piece slots a vanilla ROM fills with tile 0xBA (a dither texture), so its event area looks emptier than the ROM's bytes, which are what the game would draw if a step used the piece. LM is showing its own normalised copy, which it writes on its first overworld save.
