  • The two SFX banks are 1DF9 and 1DFC — SMW's two sound-effect ports. Per AMK's docs the only difference between them is the SPC channel used (#6 vs #7). $1DFA is echo control and $1DFB is song upload.
  • Addmusic_sound effects.txt declares SFX as <hex slot> [flag] TAB <filename>, resolved against the same-named folder. * = emit the slot as a pointer to an already-inserted effect (saves ARAM); ? = suppress AMK's auto-appended $00 terminator.
  • The real SFX sources are pure $xx hex — not a single note letter across all 93 files. Grammar is: length byte, optional volume, optional second volume (= L/R pan), then a note byte ≥ $80; bare notes inherit the previous header.
  • ARAM is the binding constraint on everything audio. Global songs never transfer but cost ARAM permanently; the echo buffer must be reserved up front ($FA $04) or you get "Echo buffer exceeded total space in ARAM"; echo delay is capped $00-$0F by ARAM cost. The docs warn a rogue echo buffer "can cause irreparable damage".
  • <ROMNAME>.msc is the Lunar Magic handoff — AMK writes it so LM knows the song list. That is a file pipe-dream will have to read or write if it ever manages music.
  • Prefers asar.dll over asar.exe, both expected in the program directory. Backs the ROM up as ROMNAME~.
  • Also worth knowing: channels 6-7 are shared with sound effects and get cut, channel 0 can't be pitch-modulated, and loops cannot nest ([[ ]] is layer two, remote event 4 is an effective third).
  • Dead data found in the shipped test corpus: test/1DFC/0E L + R scroll.txt and 1DFC/1D Time low 2.txt each hold a mid-stream $00 followed by a verbatim copy of a 1DF9 effect. A zero length byte ends the effect, so those trailing blocks are unreachable. Flagged AMBIGUOUS in the graph — verify against SoundEffect.cpp before citing it.

What AMK does (the facts we work from)

From the documentation, not the source.

  • A song is a text file of up to 8 channels (#0-#7; 6 and 7 are shared with sound effects and cut when one plays). Notes cdefgab r ^ with +/-, lengths as note values, l default length, o < > octave (1-6), h tuning, { } triplets, @ instrument (0-18, 21-29, 30+ custom), v/w channel and global volume, y pan (0-20, optional surround flags), q quantisation, t tempo, p vibrato, n noise, & pitch slide, ? no loop, / intro marker, ("x.brr",$tt) sample load.
  • Loops: [ ]n, labelled (n)[ ]m and (n)k calls, * recall; none nest, but [[ ]]n superloops nest around them and a remote-code event type 4 is an effective third level.
  • Remote code: (!n)[...] defines hex commands with no notes; (!n, type, arg) attaches one to an event (note on, N ticks into a note, before a note ends, key off, run now, disable).
  • = replacements (greedy, recursive, only for text after them), and preprocessing (#define #undef #ifdef #ifndef #if #endif #error) that runs before everything else.
  • Hex commands: 106 rows in hex_command_reference.html ($DA instrument ... $E0-$E4 volume, tempo, transpose, $E5 tremolo, $E6 subloops, and AMK's $FA family). They are validated unless -h is given; validation turning off also turns echo bounds checking and AM4/AMM conversion off.
  • Directives: #samples { #group "x.brr" ... }, #instruments { "x.brr" $aa $bb $cc $dd $ee } (ADSR1 ≥ $80 selects ADSR else GAIN; dd.ee tuning), #path, #pad, #halvetempo, #option tempoimmunity | dividetempo n | smwvtable | noloop, #spc { #author ... #length }, #amk n (parser version, appended when absent; #am4 and #amm override it).
  • Samples: BRR files, grouped in Addmusic_sample groups.txt. #default is every stock SMW sample, #optimized only those global songs and sound effects need. A trailing ! marks a sample "important" (always resident). Unused samples are dropped per song unless -u; duplicates are shared unless -d.
  • Global and local songs in Addmusic_list.txt: globals never transfer and cost ARAM permanently; locals upload on a song change, with their samples unless $1DFB's caller keeps the old set.
  • Sound effects: two folders, 1DF9 (SPC channel 6) and 1DFC (channel 7), listed in Addmusic_sound effects.txt with * (pointer to another effect) and ? (no auto $00). Commands are the note subset plus @x, @x,y noise, v x,y, raw $xx, and #asm/#jsr inline SPC700.
  • The SMW side: writing $1DFB uploads a song ($FF or a missing song fades out); $1DFA #$06 turns sound-effect echo on, #$05 off (default off); echo is disabled on upload and the echo buffer must be reserved or the build stops with "Echo buffer exceeded total space in ARAM".
  • ROM side: data goes in RATS-tagged free space beyond SMW's own, preferring banks $40+ on a 4 MB ROM (-b turns that off); -a takes untagged space too; -p writes the patch and files without touching the ROM; -norom makes .spc files alone. A Addmusic_options.txt replaces the arguments.
  • Conversion: AddmusicM songs need an #amm header and an sXX_.. line rewritten as a #samples list; Addmusic 4.05 songs need #am4; .bnk sample banks are named in #samples.

Clean-room boundary

The compiler and the engine are written from the section above and from the hex command reference, not from AMK's source. Anyone writing them should not have AddmusicK/*.cpp, Music/, MML/, Binary/ or test/asm/*.asm open; gaps go to the oracle (compile and compare), Mesen, or the SMW disassembly's own sound notes. Disclosure: the author of this plan read AddmusicK.cpp's function list, its command-line option parsing, generateMSC, the two short functions that assemble the SNES patch and the SPC program (they only name files and scan them for a few labels), and the docs above, and nothing deeper. The shipped docs and the CLI flags are public behaviour, so that is within the rule, but a later reader should still start from this file and not from that source.

Open questions

  1. Which AMK? The docs here describe the HertzDevil fork of 1.0.5. Later releases (1.0.9, 1.0.10, 1.1) added hex commands and options. Do we target 1.0.5 as the floor and add later features when a song needs them, or pick a newer version's documentation first?
  2. The oracle's version. Output differs between releases. The oracle is the local 1.0.5 build; a song that relies on a later feature will not compile there and has no oracle.
  3. Does the bundled Quasar assemble spc700? Yes (2026-10-21). norom + arch spc700 + org $0000 + base $0200 gives flat bytes at file offset 0 and labels at their ARAM addresses, through Asar.Patch on an in-memory buffer (Spc700AsarTests). Syntax notes for the engine's author: no ! absolute prefix (the operand's size picks direct page or absolute; .b/.w force it), and immediate,dp stores are written mov $f2,#$6c, tset/tclr take the accumulator (tset $0030,a), and adc a,x is not an instruction (adc a,(x) is).
  4. Engine compatibility without AMK's engine. Songs depend on AMK's engine details (timing of fades, slides, the velocity table, how q and ties interact). The hex reference and the oracle pin most of it; some will only show up as songs that sound different. How much divergence is acceptable, and is "same DSP writes in the interpreter" the bar?
  5. ARAM layout. Songs that fit AMK might not fit ours, or the reverse, if our engine is bigger or smaller. The echo-bounds check will report that honestly, but it can change which songs build.
  6. ROM space. AMK writes into RATS-tagged free space and prefers $40+ on 4 MB ROMs. How does that sit with RatsWriter and the sprite driver's data?
  7. Existing music on the base. A base already carrying AMK's data (any ROM made with AMK) must be refused or cleaned, as a PIXI-patched base is by the sprite driver (STSD check). What marks AMK's insertion, and does cleaning it need the tool's own undo?
  8. Preview scope. Is an in-app player worth its cost, or is Mesen plus .spc export enough?
  9. Sample sources. BRR is the only format. Do we want WAV import (resample and encode to BRR) later? AMK itself has none.

The music engine: what AddmusicK's does, as measured, and what ours must do

Working notes for AMK_PORT.md phase 5. Everything here was read off AddmusicK's behaviour (its songs run in rom/Spc700.cs, the DSP writes read back by rom/SpcTrace.cs, tools/amk/amk_events.py, amk_voice.py and the ad-hoc comparison in tests/MusicEngineTests.cs), or taken from its documentation (doc/readme_files/*.html), never from its engine source. Our engine is data/musicdriver/main.asm, SPC700 code of our own assembled by Asar's spc700 mode, tested by playing the same song in both engines and comparing what each tells the DSP.

How the two engines are compared

MusicEngineTests.Differences: for each voice, the key-ons in order (pitch, sample, ADSR, GAIN exact; volume within 1), the gap from each key-on and key-off to the one before (within 1.5 ticks + 6%), volume and pitch at fixed points into each note (against theirs over a quarter tick either side; pitch within 1/128 of itself), and each song-wide DSP register's sequence of values. corpus_report (PIPEDREAM_ENGINE_REPORT=1) runs the whole oracle corpus; adhoc (tools/amk/adhoc.sh FILE) any song; load (PIPEDREAM_MML) profiles our engine's time.

The interpreter's instruction and timer timing were checked against blargg's snes_spc in libgme (tools/amk/cycle_check.py): every instruction group and the timer counter's overflow agree to the cycle.

Where AddmusicK's engine is not the reference

  • It falls behind. With many channels running effects it cannot finish a tick inside a timer tick and loses some: about 1% with six vibrato channels, 5% on dv.mml, 23% on ek.mml (t192, eight channels). snes_spc agrees, so hardware would too. Ours keeps time (effects run once per main-loop pass, unchanged pitches are not resent), so the comparison times each event from the one before, not from the start.
  • $DD straight after a loop's end, or before any note, stops the song for good (exp2.mml). Not copied.
  • $E5 with depth $FF after a note hangs it. Not copied.

Timing

  • Timer 0 runs at 500 Hz (target 16). Each timer tick adds tempo + 1 to a one-byte accumulator; a carry is a song tick: ticks per second = 500/256 × (T+1). A quarter note is 48 ticks. With no t, the tempo is 53.
  • Effects (vibrato, bends, pan fades, tremolo) move every timer tick, the time into the note being song ticks plus the accumulator's fraction. Bends, tremolo and pan fades run one timer tick (or tick) ahead, as measured.
  • The first channel to reach the end of its data ends the phrase for every channel; notes others started that tick are dropped, and the next phrase starts on the same tick. A new phrase keeps each channel's instrument, volume, pan and q.

Notes

  • Quantisation: a note is released at tick max(len × T[q] >> 8, 1) and again at len − 2, T = 33 66 80 99 B3 CC E6 FF. Rests are released at their start and get the same two. A release is skipped when a tie follows (durations, q bytes and commands stepped over; a call, loop, arpeggio or the end of data counts as no tie).
  • Pitch: the top octave from a 12-entry table (085F ... 0FCD, then 10BE), a fraction of a semitone interpolating between neighbours there (truncated), each octave below half the one above, then × the instrument's tuning (P × whole + (P × fraction >> 8)).
  • Transposition: $FA $02 (channel) and $E4 (all) add semitones; the sum wraps in seven bits ($85 is +5, $7B is −5), and a result past the top note plays at pitch 0. Percussion is transposed too.
  • $EE f: f/256 of a semitone on every note.
  • Instruments: @0-@18 SMW's; @19 and @20 leave the instrument as it is; @21-@29 are percussion: each plays a fixed note (A8 A4 A1 A4 A4 9C A6 A6 A1) on its own instrument (tuning 3 7 7 7 8 2 8 8 3), and the channel keeps that instrument for later notes. No @ at all plays @0.
  • $ED: aa < $80: ADSR1 = aa | $80, ADSR2; $80 gg: ADSR1 = 0 and GAIN = gg. $FA $01 gg: ADSR1 &= $7F, GAIN = gg. $F4 $09 or a new @ undoes both.

Volume

  • P = ((((v × vel) >> 8) × w) >> 8)² >> 9; $FA $03 a makes it P + (P × a >> 8); then left = P × pan[y] >> 7, right = P × pan[20 − y] >> 7, pan = 00 01 03 07 0D 15 1E 29 34 42 51 5E 67 6E 73 77 7A 7C 7D 7E 7F (interpolated, truncated, while a pan fades). A surround bit flips that side's sign. Defaults: w 192, v 255, y 10, velocity table N-SPC's.
  • A v, y, w or $FA $03 change is sent on its tick, mid-note too.

Effects

  • Vibrato $DE d r a: after d ticks, phase = (t − d) × r; a triangle, +a/256 semitone at a quarter, −a/256 at three quarters. $EA n: the depth grows from 0 at key-on over n ticks. $DF returns the note to its pitch.
  • Bend $DD d l n (read with the note just before it): from the note to n, starting d ticks in, over l ticks, linear in semitones; then held at n.
  • $EB d l s / $EC d l s: every later note bends by s semitones (release), or starts at note − s and bends back (attack). A length of 0 turns them off.
  • Tremolo $E5 d r a: volume × (1 − a/256 × u), u a triangle from 0 up to 1 at half a period; phase (t + 1 − d) × r. It applies at key-on too. Depth 0 turns it off.
  • Fades $E8 volume, $DC pan, $E1 global volume, $E3 tempo: a signed 8.8 step a tick, the first on the tick the command is read, landing on the target. A length of 0 does nothing. Volume steps per tick; a pan fade also glides between ticks.

Echo

  • At song start and every time the phrase list loops: FLG $60, ESA $FF, EDL 0, FLG $40, FLG $00; the buffer reserved is forgotten.
  • $EF (as compiled: channels, left, right become EON, EVOL L, EVOL R in the byte order AddmusicK stores them).
  • $F1 d f n: if d is beyond the buffer already made: FLG $60, ESA = $100 − 8d ($FF for 0), EDL = d, then the whole song stands still for 13 × d timer ticks, FLG $40, another 13 × d, FLG $00. Otherwise just EDL. Then EFB = f, the eight FIR coefficients from filter n (0: FF 08 17 24 24 17 08 FF, 1: 7F 00 ..., 2: 5F 08 DE 08 65 09 F4 09), and the echo volumes again.
  • $FA $04 n makes the buffer for delay n up front (with the same wait) so later $F1s up to n do not pause.
  • $F0: EON, EVOL 0, FLG $20. $F2 l L R: echo volume fade, one step fewer than l, not landing on the target. $F5: the eight FIR coefficients. $F4 $03: this channel's echo bit toggled.
  • PMON, NON and EON are written every song tick.
