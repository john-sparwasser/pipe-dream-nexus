  • Sprite slots are fixed ranges: normal 00-BF, per-level B0-BF, shooters C0-CF, generators D0-DF, plus cluster, extended and misc types. list.txt groups them with type headlines (SPRITE:, CLUSTER:, EXTENDED: …).
  • Four different "extra data" concepts, easy to confuse: tweak bytes, extra property bytes, extra bytes, shooter extra bytes, and the indirect data pointer. The indirect pointer exists because Lunar Magic caps per-sprite data at 12 bytes — that cap is a constraint on us too.

  • Bundles Asar v1.91 via CMake FetchContent and links it — the concrete example of embedding Asar in another tool.
  • Also exposes a library API with C/C++/C#/Python bindings plus a C-ABI plugin system.

Custom sprites: bringing PIXI into Pipe Dream

Plan for doing PIXI's job (custom sprite insertion, JackTheSpades/SpriteToolSuperDelux 1.43) inside Pipe Dream, with a library window like Custom blocks and Patches and a sprite editor for each sprite's JSON. Started 2026-10-19. Modelled on custom blocks (GPS_PORT.md) and patches (PATCHES.md). Background on PIXI's files is in ROM_TOOLING.md § "PIXI — what to look at"; this file is the plan and its decision log.

What PIXI does, which is what we have to do

Facts from the research of 2026-10-19 against PIXI master 734b8ed (paths relative to that repo). Format facts only; promote to CONTRACT.md as [CONFIRMED] once measured in Mesen.

  1. Read the list (list.txt): NN file, per-level LLL:NN file (B0-BF), section headers. In SPRITE:, slots below C0 read from sprites/, C0-CF from shooters/, D0+ from generators/; only C0-DF run as custom shooters/generators.
  2. Read each config. CFG lines: type (0 tweak, 1 custom, 2 shooter/generator), acts-like, the six tweaker bytes $1656 $1662 $166E $167A $1686 $190F, extra property bytes 1-2, ASM file, a:b extra-byte counts (extra bit clear:set, hex, ≤ 0C). JSON: the same, with each tweaker byte an object of named fields (src/json_const.h has the exact names, typos included: "Don't disable cliping when starkilled"), byte counts in decimal, plus Map16 (base64, 8 bytes per 16×16 tile: TL, BL, TR, BR tile words), DisplayType (XY/ExByte), Displays (description, extra bit, position nibble X/Y 0-F or extension byte Index/Value, then text or Tiles: signed pixel offsets + Map16 tile number), and Collection (name, extra bit, up to 12 extra-byte values: Lunar Magic's sprite list).
  3. Assemble each sprite with Asar: a wrapper giving it SA-1/base defines, the shared routines as %Name() macros, its folder's _header.asm, then freecode and the sprite. INIT and MAIN come back as Asar prints (print "INIT ",pc); status entry points (CARRIABLE, KICKED, CARRIED, MOUTH, GOAL) likewise.
  4. Insert routines once: each routine used is put in freespace once and its address kept in a table, so every sprite's macro JSLs the same copy.
  5. Write the tables: the header at $02FFE2 ("STSD", version, flags, dl table, per-level pointers, status pointers); the global table, 0x100 × 0x10 bytes (type, acts-like, six tweakers, INIT 24-bit, MAIN 24-bit, two extra property bytes; empty = $018021, an RTL); per-level tables keyed by $010B; Lunar Magic's sprite size table ($0EF30C: dl Size : db $42, 0x400 bytes, 3 + count per (extra bit, number)).
  6. Hook the game: init $018172, main $0185C3, the extra-bits keepers ($02A963, $02A94B, $02A9C9), the table setter $0187A7, shooter/generator load and run, the status handler $018127, and the sprite-data offset $02A846 that reads the size table. A sprite is custom when its level-data extra bit $08 is set.
  7. Fix the levels whose sprite records changed length (PIXI's MeiMei), since a level's sprite list is walked with the size table.
  8. Write Lunar Magic's aux files (.ssc, .mwt, .mw2, .s16) so LM shows the sprites.

Phases

1. Model, import, session API — no insertion

  • ProjectFile.Sprites (library: name → { Config, Source, Files }, Config the JSON) and ProjectFile.SpriteSlots (global NN and per-level LLL:NN → library name).
  • data/PixiConfig.cs: parse and write the JSON (every field, named tweaker bits), CFG → JSON.
  • Import a PIXI folder: list.txt → slots, configs → JSON, each sprite's ASM and the files it includes, routines/ and ExtraDefines/ into the project as user data.
  • services/EditorSession.Sprites… (name chosen to sit beside the existing sprite partials): list, new, import, set config, set source, delete, assign slot — each returning a status.
  • Tests: CFG → JSON for every field; JSON round trip byte-identical on PIXI's own examples; folder import (list.txt with per-level lines, shooters, generators, includes).
  • Status (2026-10-19): done. data/PixiConfig.cs (parse, write, FromCfg; the tweaker fields are a table of PIXI's names and bits), data/PixiImport.cs (slots, one sprite, a folder), ProjectFile.Sprites/SpriteSlots/PixiFiles, services/EditorSession.CustomSprites.cs, tests/PixiTests.cs. The round trip is ours, not PIXI's: written JSON reads back and writes again byte for byte, laid out as PIXI's example (two-space indent, every key); a file from elsewhere is normalised to that layout on import, keys we do not model dropped. A sprite keeps its file's name ("sub/thing" from a subfolder); a shooter sharing a sprite's name becomes "name (shooter)". A .cfg gets the two "(extra bit clear/set)" list entries PIXI shows it under. Cluster, extended and the misc sections of list.txt are skipped with a count.

2. Our driver and the build step

  • data/spritedriver/: hooks, tables and the STSD header for normal sprites, per-level B0-BF, shooters and generators; size table from the configs' counts; routines inserted once.
  • RomBuilder: insert after custom blocks, before patches (a patch may hook a sprite). Errors fail the build naming the sprite; overlaps with prep's hooks are checked like patches'. Prep's hooks near PIXI's must be checked first: prep owns $05D8F5 (sprite bank) and LM's level-word mirror at $05D8E2; PIXI writes $010B from $05D8B9.
  • Levels: every level whose sprites use a number whose record length changed is re-encoded (MeiMei's job), not only the levels the project edits.
  • Tests (Asar): a sprite's INIT/MAIN land in the table; tweakers land; a disabled/unslotted sprite does not; per-level overrides global; size table matches counts. Mesen: a custom sprite placed in level 105 runs (its MAIN writes a marker byte), 3/3.
  • Status (2026-10-19): done — global sprites, per-level B0-BF, shooters and generators. Per-level sprites use a layout of our own, not PIXI's (the header says none): the table is the 0x100 global entries then 16 per level that has its own, and LevelBlocks (a word per level, keyed by $010B) gives a level's block less B0's offset, so every lookup is base + number × 16 (EntryOf). With any per-level sprite, B0-BF records are 4 extra bytes in every level, as PIXI has them: the size table is per number, not per level. Custom shooters and generators branch off at $02A866, SMW's first test of the number, before it would read D0-D9 as its own generators or DA-DF as shells: a shooter keeps its number (C0-CF) in $1783 where SMW's are 1-2, and runs from $02B395 with its timer counted down as SMW's are (PIXI's shooters test and set it, never count it); a generator keeps D0-DF in $18B9 where SMW's are 1-F, and runs from $02AFFE unless sprites are frozen. $02B3AB could not be the shooter hook: the JSL $0086DF after it reads its own return address as the table. Measured in Mesen, 3/3 each, on level 105: level 105's own B0 ran where a global B0 also exists; a custom shooter C0 and a generator D0 each ran MAIN 60 times in 60 frames.
  • Global sprites, first pass: data/spritedriver/ (main.asm, defines.asm), data/SpriteInsert.cs, RomBuilder.InsertSprites, tests/SpriteInsertTests.cs. What the vanilla code at each hook turned out to be, read with --disasm on a v34 base:
    • $02A846 is Lunar Magic's record step on a prepped base (JML $1E9185: INX : INY : INY, then a BPL that rebases $CE past $80), fixed at 3 bytes — nothing in the game read the size table before the driver. Ours steps by the table and chains to LM's code past those three bytes (or to $02A82E on SMW's own loader).
    • $02A94B/$02A963 store byte0 AND #$0D into a position-high byte ($14E0 vertical, $14D4 from LM's horizontal path, whose caller then ANDs A with 1): the extra bits would land in the position. Ours keeps bit 0 there and the extra bits in !extra_bits.
    • $02A9C9 is the spawn's JSL $07F7D2 (clear the slot, then SMW's tweakers by $9E); $07F785 is that clear's tail, where the custom state is cleared with it.
    • $0187A7 is sprite 9B's INIT stub (via $0182B3); it moves to a copy at $01FFF0, and $0187A7 becomes the "give this slot its custom tables" call spawning sprites make.
    • Custom INIT/MAIN are entered through JML [$00] from a JSL, and come back to bank 01 through the RTS at $0185C2. Measured in Mesen on level 105 (walk left, enter): INIT stored $11 and the placement's first extra byte $AB, MAIN counted exactly 60 in 60 frames — 3/3; the level's own sprites still load and live walking right. Testing this found an existing bug, fixed separately: the build wrote a level's sprites unsorted, and the loader never reaches a record placed left of an earlier one. Not yet: the CARRIABLE/KICKED… status entry points, VERG checks, the silver-POW coin path reading SMW's table by the custom number.

5. Parity and the rest

  • Status entry points, the 255-sprites-per-level remap, Lunar Magic's aux files on build (all done; see below).
  • Cluster, extended, minor extended, bounce, smoke, spinning coin, score.
  • MIT versions of the routines (done; see below).
  • Status entry points (2026-10-19): done. A sprite may print CARRIABLE (status 09), KICKED (0A), CARRIED (0B), MOUTH (07) and GOAL (0C), as PIXI's README has them; the printed code then runs in that status in place of SMW's, entered with the data bank set to its own, and a status it does not print runs SMW's code as before. The second extra property byte still overrides: bit 7 runs MAIN instead, bit 6 runs MAIN first (then the sprite's entry or SMW's). The pointers are a StatusTable of our own, laid out as the sprite table (five longs and a pad byte per entry, per-level blocks included) so EntryOf finds both; the STSD header's status pointer stays $FFFFFF, since a tool reading it would expect PIXI's layout. Measured in Mesen on level 105, 3/3: a sprite whose INIT sets status 09 ran CARRIABLE 120 times in 120 frames with the data bank at its code's ($90), and not MAIN.
  • Lunar Magic's aux files (2026-10-19): done. data/SpriteAuxFiles: every build writes <name>.ssc, .mwt, .mw2 and .s16 beside build/<name>.smc from the global slots' configs (a build without any removes the last build's). Formats from Lunar Magic 3.40's help (Lunar Magic.chm: "Custom Tooltips for Sprites", "Custom Collections of Sprites", "Custom Map16 for Sprites"), then compared with PIXI 1.43's own output for two real sets on this machine: Tempest's two JSON sprites came out byte-identical in all four files; QLDC2023's 31 JSON sprites identical in .mwt, .s16 and every tile line, with two differences that are PIXI bugs we do not copy: PIXI writes a description's line break raw into the .ssc (ending the line mid-text), where we write LM's \n escape, and it fills extra bytes past a Collection entry's four from stale memory (.mw2 held the bytes of "tra", "By", "Ext"), where we write the entry's. Facts the help leaves out, as PIXI writes them:
    • .ssc fields are space-separated (the help says tab; LM reads both), lines end CRLF; .mwt is tab-separated, CRLF, the number only on a sprite's first entry.
    • TYPE is Y nibble, X nibble, then 20/30 (extra bit clear/set) + 0 description, 2 tiles, 8 GFX files; by extension byte, the byte's number counting the three record bytes (Index + 3), two hex digits of value, then the same. Tile numbers and GFX files in hex.
    • .mw2 records are 70|extra<<2|1, 70, number, bytes… — every one flags "next group", so each Collection entry is its own list item — after a 00 header, ending FF.
    • .s16 starts at sprite tile 0x400 and is 0x10 pages (PIXI's size; LM saves 0x38). Each sprite's own tiles go in slot order and its display tiles from 0x300 are renumbered there.
    • PIXI writes nothing for a .cfg sprite; ours are JSON by then, so a converted one is listed under its two "(extra bit clear/set)" entries. Not done: appending a base's own aux files (a project copies only the ROM), the overworld's .sscov/.s16ov, extmod. Opened in Lunar Magic 3.40 (2026-10-21): Secret's four PIXI 1.40 sprites built on our routines, 150 sprites in level 105 - display tiles, tooltips and the Add Sprites list all show, the level saves with no 128 warning and plays. Against pixi.exe 1.40 on the same list the .ssc is identical, the .mwt/.mw2 differ only by the converted .cfg entries, and its .s16 is ours padded with zeros to 0x1C000. Found on the way: a config whose Map16 is not base64 (QLDC2023's CapeShell says "Cape Shell") was refused at import; it now reads as no tiles, as PIXI does.
  • Cluster and extended sprites (2026-10-19): done. ASM alone (no config), slotted in lists of their own, cluster NN / extended NN (00-7F); a PIXI folder's CLUSTER: and EXTENDED: sections import into them, with cluster/ and extended/ _header.asm. Each must print MAIN; an extended one may print CAPE. The interface, from PIXI's README and real sprites (Ladida's cluster package, UberASM's defines): a custom number is the list number plus !ClusterOffset = $09 / !ExtendedOffset = $13, the sprite or its spawner storing it in $1892 / $170B itself (bit 7 of a cluster number is its extra bit). Those offsets are SMW's table sizes, read off its dispatchers: the cluster jump table at $02F825 has entries 00-08, the extended one at $029B2B 00-12. Hooks: $02F815 (the cluster loop's LDA $1892,X : BEQ) and $029B16 (the extended loop's LDA $170B,X : BEQ) send a custom number to its MAIN from ClusterTable / ExtendedTable (0x80 longs each); an extended one's timer $176F counts down first, as SMW's do. Entered with X = Y = the slot and the data bank set to the code's: a real cluster sprite (lava.asm) indexes with Y and reads its tables without setting the bank. SMW reads the number as an index in one other place, found by scanning for every $170B/$1892 read: the cape's check of extended sprites at $029636, whose clipping ($02A519) is a table by number. That is hooked too: a custom one runs its CAPE, or nothing (PIXI's README: without one "cape interaction ... do nothing"). The rest compare against fixed numbers or look for a free slot. Measured in Mesen on level 105, 3/3: a sprite's INIT put cluster 02 in cluster slot 3 and extended 00 in extended slot 5; the cluster MAIN ran 121 times and the extended 119 in 120 frames (the extended loop runs before the spawn that frame), with the data bank $90 and the slot in Y (cluster) and X (extended). The cape path is in the table test only. (The minor kinds came next; see below.) Defines checked against PIXI's own defines file (asm/sa1def.asm, read for names and values only): !ExtendedSize is $08 (!ExSprSize+1 — spawning keeps off slots 8-9, Mario's fireballs), cluster speed tables are !cluster_misc_1e52… by address, !Bank8 is $80. The same file gives the minor kinds' offsets for later: minor extended $0C, bounce $08, smoke $06, spinning coin $02, score $16; its spawn routines (routines/Spawn/*Generic) store A as the number, so the caller adds the offset. Since PIXI 1.41 its !1938 is the remapped $7FAF00 and disabling the remap is an error; ours is too (the remap, below).
  • Minor extended, bounce, smoke, spinning coin and score sprites (2026-10-19): done. As cluster and extended: ASM alone, MAIN only, slotted as minorextended NN, bounce NN, smoke NN, spinningcoin NN, score NN (the kind is its list.txt section's name, lower case), imported from those sections out of misc_sprites/<kind>/ with its _header.asm. PIXI's README names the sections and folders and nothing more: not the entry points, the registers or how the number is stored, so the interface is the cluster one, and the offsets are SMW's counts (above). Every place SMW reads the five number tables ($17F0, $1699, $17C0, $17D0, $16E1) was listed by scanning for each read; all but one per kind look for a free slot or compare with a fixed number, and the one is each kind's dispatch, hooked at its LDA number,X : BEQ:
    • minor extended $028B69 (12 entries in SMW's jump table, matching $0C);
    • bounce $02904D, the top of the dispatch the bounce/smoke loop JSRs; a custom one's timer $16C5 counts down first, as the dispatch does for SMW's;
    • smoke $0296C0, whose next instruction drops bit 7 (a flag), so a custom smoke number is masked the same way and its list stops at 7F - $06 (cluster's, for its extra bit, at 7F - $09; the rest have 0x80);
    • spinning coin $0299D7 and score $02ADBD, loops that JSR to SMW's one routine each (score's reads its tables by number). Each runs MAIN through CallLong, every frame, frozen or not (SMW's check $9D themselves), with X = Y = the slot and the data bank its code's; minor extended also sets $1698 to the slot as SMW's loop does. The table loads are a %call_listed() macro now, cluster and extended included (same bytes). Measured in Mesen, 3/3 each, in the level the probe's walk left reaches: a number written into a slot of each kind ran its MAIN 60 times in 60 frames with X the slot and the data bank $90; SMW's own smoke 01, score 01 and spinning coin 01 written the same way ran their own code and emptied their slots. The probe must wait for the level's message box ($1426) to close: while it is open no sprite runs.
  • 255 sprites a level (2026-10-20): done. SMW's load table $1938 (a byte per level sprite list record, by its index $161A,x: spawned, so not again) is 128 bytes, so a 129th record wrote into the screen exits at $19B8. As PIXI has it since 1.2.15 (its changelog and asm/sa1def.asm, names only): the table is $7FAF00, 256 bytes, !1938 means it, and index FF stays "not from the level". Every instruction addressing $1938 was found by scanning a built ROM for each absolute opcode with that operand (no long ones exist; the three hits in bank 0D are tile data; Lunar Magic's bank-1E loader never touches it and jumps back only to $02A846/$02A84B/$02A856). Nine sites, each now calling the driver ("The load table" in main.asm): the loader's test-and-mark $02A856; the level-load clear $02ABF2 (64 bytes in SMW, 128 after Lunar Magic's $02ABF3 = $7F, 256 now); a generator's record left unmarked $02A8BB (and the driver's custom-generator branch); no free slot $02A936; $02FAE6 by $0FBC,y; and the six LDA #$00 : STA $1938,y that free a record ($01AC9C the off-screen erase, $02AB99 a shooter's, $02D088, $02FF15, $038712, $03B8BA). The editor never capped a level at 128. Lunar Magic is told the limit is 255 by clearing bit 0 of $0FFFE0: its help ("Custom Sprite List Sizes") says "0x801E0 PC", and Lunar Magic's PC offsets count the copier header (its 0x7750C is the $0EF30C size-table pointer); every PIXI ROM on this machine has $FE there, an LM-saved hack without PIXI $FF. Measured in Mesen, 3/3 each, on level 105: the probe sprite spawned with its entry marked, both as record 00 and as record 8C (140, after 140 generator records); nothing wrote $7E1938-$7E19B7 after boot; and a level sprite pushed two screens off was erased by its own off-screen check and its entry went from 1 to 0, so it can come back. Asar here assembles BNE $02A846 (an absolute operand) as an offset of $46; branch to a label, or JML.
  • Shared routines of our own (2026-10-20): done. All 27 of PIXI 1.2.x's routines, MIT, in data/spritedriver/routines/, and its sa1def.asm macros (BES, BEC, Between, debugmsg, the two define_*) in defines.asm; not invoke_snes/invoke_sa1, which are SA-1 only. Clean room, as the driver: a separate pass read PIXI's routines and wrote their observable behaviour into reference/PIXI_ROUTINES.md (no code); ours were written from that and SMW's own code, tables from SMW's ROM at assembly time (read1()) or from a formula (Aiming's 1/√k). PIXI shared routines: interface contracts

These are clean-room interface contracts for the 27 shared sprite routines that ship with PIXI 1.2.x (routines/*.asm, each one inserted once and called with JSL through %Name()). I wrote them from the routines' observable behaviour. Each contract says what a caller can see: inputs, outputs, RAM written, flags, stack effects and edge cases. The file holds no PIXI code: no instruction sequences, no paraphrase of PIXI's code instruction by instruction, no PIXI comments, and no PIXI data tables. A table is described only when it is SMW's own (its address is cited) or when it can be defined by a formula.

  • Date: 2026-10-20
  • Source read: D:\SMW\Projects\BigEye\Sprites\routines\*.asm (the same files are in every project's routines folder)
  • SMW addresses were checked against D:\SMW\Projects\.resources\SMW.smc with the PipeDream disassembler.

Conventions that apply to every routine

  • Build. The contracts describe the LoROM, non-SA-1 build. RAM is named by its SMW address: sprite tables are $E4,x, $14E0,x, etc.; "slot" means a normal-sprite slot 0..$0B. The SA-1 build moves the sprite tables (!addr = $6000 and so on), uses the SA-1 arithmetic unit instead of $4202/$211B, and uses $40/$41 instead of $7E/$7F for Map16. These differences are noted briefly where they apply.
  • Returning. Every routine is entered with JSL and returns with RTL, unless "Stack" says otherwise.
  • Direct page. D = $0000 is assumed: $00-$FF is RAM $7E:0000-00FF.
  • Data bank. "DB must map WRAM" means DB must be a bank where $0000-$1FFF mirrors low WRAM ($00-$3F or $80-$BF). Every routine that reads a sprite table with absolute addressing needs this.
  • Widths. "8/8" means the routine expects M=1 (8-bit A) and X=1 (8-bit X/Y) on entry. Most of them do. When a routine runs with the wrong widths, its immediate operands shift and the result is garbage, so treat 8/8 as a hard precondition unless the contract says otherwise.
  • B. The high byte of the accumulator, which XBA exposes. It is listed only where it is deterministic and might be relied on. Otherwise it is a by-product.
  • Flags. Any flag not listed under Returns is a by-product. V is a by-product everywhere. A differential test should mask by-product flags. Flags that are listed are exact.
  • EXLEVEL. PIXI decides at assembly time whether Lunar Magic's tall-level support is present (!EXLEVEL). It reads the Lunar Magic version string at ROM $0FF0B4; versions above 2.53 set it. Every ROM saved by Lunar Magic 3.x takes the EXLEVEL branch, so that branch is the one that matters for current ROMs. SubOffScreen, GetMap16 and ChangeMap16 behave differently depending on this flag.
  • SMW routines called. These belong to the ROM, not to PIXI. A reimplementation may call the same addresses:
    • $01ACF9: random number generator.
    • $02A9DE: find a free slot, keeping 2 slots in reserve.
    • $03B664: player clipping, box B.
    • $03B69F: sprite clipping, box A.
    • $03B72B: box-vs-box contact test; returns C.
    • $07F7D2: initialise a slot's tables.
    • $0187A7: give a slot its custom tables. This address is PIXI's driver hook, not vanilla SMW code.
    • $02ACE5: give points.
    • $01AB6F: contact sound and contact graphic.
    • $02A469: extended sprite hurts the player.
    • $02B554/$02B560: extended sprite X/Y speed. These end in RTS.
    • $00C0FB: queue a Map16 tile to VRAM. Ends in RTS.

PIXI reaches the RTS-ending routines ($02B554/$02B560, $00C0FB) from another bank with the usual "push a long return address, then push the address of an RTL in the target bank minus 1" trick. The RTL bytes it uses are at $00804D and $02B889. Any equivalent call mechanism is acceptable.

  • Box layout used by SMW's contact test $03B72B. Box A is $04 x-low, $0A x-high, $05 y-low, $0B y-high, $06 width, $07 height. Box B is $00, $08, $01, $09, $02, $03 in the same order. $03B72B preserves X and Y, clobbers $0C and $0F, and returns C=1 on contact.

Aiming

Computes an 8-bit X speed and Y speed of magnitude about speed, pointing from the shooter toward the target.

  • Called with:
    • Any register widths. The routine saves P and sets 8/8 itself.
    • A (low byte) = speed s, unsigned.
    • $00-$01 = 16-bit dx = shooter X − target X.
    • $02-$03 = 16-bit dy = shooter Y − target Y.
    • DB is irrelevant.
  • Returns:
    • $00 = X speed (8-bit). $02 = Y speed (8-bit). $01 = $03 = 0.
    • Each output is the value computed below, not negated when its input d had bit 15 set (target to the right / below), and two's-complement negated when bit 15 was clear. d = 0 gives a negated 0, which is 0.
    • P is restored exactly as on entry, so widths and C/V/D/I are the entry values, except that N and Z reflect the restored X.
    • X is preserved. Y is untouched.
    • A low byte = the final $00. B = high byte of the 16-bit Vx below.
  • Scratch RAM: $04-$05 = S (16-bit, defined below). $06 = 1 if dx was negative, otherwise 0. $07 = 0. $0F = s. The multiplier registers $4202/$4203/$4216/$4217 are left holding the last product.
  • Algorithm:
    1. Take absolute values: two's-complement negate dx or dy if bit 15 is set. $8000 stays $8000 and is then treated as unsigned.
    2. While (|dx| OR |dy|) ≥ $100, shift both right by 1. The shift count is the bit-length of the high byte of the OR. After this, ax, ay ≤ $FF.
    3. d = ax² + ay², a 17-bit unsigned value.
    4. Choose sh as the smallest value in 0..5 with d >> (2·sh) < $100. The six bands are d < $100, < $400, < $1000, < $4000, < $10000, and ≥ $10000. Then k = d >> (2·sh) and m = R[k] >> sh (16-bit logical shift).
    5. S = floor(s · m / 256). This is exact and always fits in 16 bits.
    6. Vy = floor(ay · S / 256) and Vx = floor(ax · S / 256), both 16-bit. The outputs are their low bytes, sign-applied as above.
  • Tables/data: R is a 256-entry table of 16-bit words: R[0] = $FFFF, and R[k] = min($FFFF, round(65536 / √k)) for k ≥ 1. All 256 entries were checked against this formula. SMW has no such table. m approximates 65536/√d, so S·a/256 ≈ s·a/√d.
  • Stack / control flow: normal.
  • Equivalent SMW code: none. (SMW's aimed projectiles use other methods.)
  • Calls: none. Uses the hardware multiplier at $4202/$4203 (SA-1: $2250-$2254/$2306-$2307). Allow 8 cycles before each product read.
  • Edge cases:
    • dx = dy = 0 gives 0, 0.
    • d = 1 uses R[1] = $FFFF.
    • The magnitude can slightly exceed s because of rounding. Only the low byte is kept, so s close to $FF can wrap.
    • The SA-1 build computes m·s through the SA-1 multiplier with a different path for m ≥ $8000. Its results are the same in intent but not guaranteed to be bit-identical, and this contract does not cover them.

CapeContact

Checks whether sprite X is touching the spinning cape.

  • Called with:
    • 8/8, X = sprite slot.
    • DB must map WRAM.
  • Returns:
    • C=1 for contact, C=0 for none. X and Y are preserved.
  • RAM written / scratch: when the box test runs: $00-$0B (both boxes), plus $0C and $0F (from $03B72B). The early "no" exits write nothing.
  • Behaviour: returns C=0 without touching RAM if any of these holds:
    • $13E8 (cape-spin active) = 0.
    • $15D0,x | $154C,x | $1FE2,x ≠ 0.
    • Layer mismatch: let L = $1632,x, with bit 0 flipped when $74 (climbing) ≠ 0. Exit if L ≠ $13F9, comparing the whole byte.

Otherwise:

  1. Box A comes from SMW's $03B69F.
  2. Box B is the cape box:
    • X = 16-bit ($13E9/$13EA) − 2, giving $00/$08. Width $14 in $02.
    • Y = $13EB/$13EC, giving $01/$09. Height $10 in $03.
  3. The result is $03B72B's.
  • Stack / control flow: the final step is a tail jump into $03B72B, so $03B72B's RTL returns to the caller.
  • Equivalent SMW code: the per-sprite body of SMW's cape-vs-sprite check, $0293CE-$0293F2. The cape box is SMW's $029696 exactly. Differences:
    • PIXI does not test $14C8,x ≥ 8 or $166E,x bit 5. SMW's surrounding loop does.
    • PIXI has no net-punch alternative box ($029663, which SMW chooses when $0E ≠ 0).
    • PIXI does not call SMW's hit handler ($029404).
  • Calls: $03B69F, $03B72B.

ChangeMap16

Writes a Map16 tile number at a level position and queues the VRAM update.

  • Called with:
    • Any X width. The accumulator holds the tile number as a full 16-bit value. Callers normally set M=0 first; with M=1, B:A is taken as the 16-bit value.
    • $98-$99 = block Y (16-bit). $9A-$9B = block X (16-bit).
    • $1933 = layer: 0 = layer 1, 1 = layer 2. Other values index garbage.
    • DB must map WRAM. $00C0FB reads $0FBE,y and $1933 absolute.
  • Returns:
    • C=0 when the tile was written. C=1 when the position was out of range and nothing was written.
    • P is otherwise restored to its entry value, except that N and Z reflect X.
    • X and Y are preserved (restored at their entry widths). DB is preserved.
  • Address computation: steps 1–3 below are identical to GetMap16's, including every scratch write and the swap of $99/$9B on vertical layers.
  • Range check: the same as GetMap16's.
  • Write:
    • $7E:addr = tile low byte.
    • $7F:addr = (tile >> 8) & $7F. Bit 15 of the tile is dropped.
  • VRAM queue: after the write, the routine calls SMW's $00C0FB with:
    • M=0, X=0.
    • Y = (tile × 2) & $FFFF, its index into the tile-pointer table at $0FBE.
    • X = the Map16 address.
    • $06/$07 = the VRAM tilemap address (step 3 of GetMap16).
    • $0C-$0F = the original block X/Y.
    • $08/$0A = camera values chosen by layer and orientation:

| layer orientation | $08 | $0A | |---|---|---| | horizontal L1 | $1A − $80 | $1C | | horizontal L2 | $1E | $20 − $80 | | vertical L1 | $1A | $1C − $80 | | vertical L2 | $1E − $80 | $20 |

The orientation is bit 0 of the value saved in $0A, which is consumed by shifting $0A right once, so $0A holds half its GetMap16 value before being overwritten. All of these are 16-bit.

$00C0FB decides whether the block is close enough to the camera to upload. If it is, it appends a stripe entry at $7F837D + [$7F837B] and adds $10 to $7F837B. It clobbers $00 and $04-$06.

  • Stack / control flow: $00C0FB ends in RTS and is reached through the bank-0 RTL at $00804D.
  • Equivalent SMW code: none as a unit. SMW's own tile changer, $00BEB0, takes a block type in $9C, not a raw tile number. The VRAM half is SMW's $00C0FB unchanged.
  • Calls: $00C0FB.
  • Edge cases:
    • Vertical layers leave $99 and $9B swapped (see GetMap16).
    • Tile ≥ $8000 is stored with bit 15 cleared, but $00C0FB receives Y = tile×2, also truncated to 16 bits.

CheckForContactAlternate

Tests two boxes for overlap with 16-bit coordinates.

  • Called with:
    • Any A width; the routine sets M=0.
    • Box 1: $00 x, $02 y, $04 w, $06 h.
    • Box 2: $08 x, $0A y, $0C w, $0E h. All values are 16-bit.
  • Returns:
    • M=1 on exit in every case.
    • C=1 for overlap, C=0 for none.
    • X and Y untouched. No RAM written.
    • N and Z come from the last 16-bit compare (by-product).
    • A holds the last 16-bit difference computed (by-product).
  • Rule: both axes must pass, X first:
    • If x1 ≥ x2, X passes when (x1 − x2) < w2. Otherwise it passes when (x2 − x1) < w1.
    • Y works the same way with y and h.

All comparisons are unsigned 16-bit, and the X axis is evaluated first.

  • Equivalent SMW code: none. SMW's $03B72B uses 8-bit boxes with a different rule.
  • Calls: none.
  • Edge cases:
    • Equal coordinates use the first branch, so a zero-width box 2 never overlaps a box with the same x.
    • There is no wrap handling: a box near $FFFF does not overlap one near $0000.

CircleX

Computes radius · cos(angle).

  • Called with:
    • 8/8.
    • $04-$05 = angle. Only 9 bits count: $05 bit 0 and $04, with $000-$1FF = 0–360°.
    • $06 = radius.
  • Returns:
    • $07-$08 = 16-bit signed X displacement.
    • M=1.
    • X preserved (N and Z reflect X).
    • C = the half-circle sign bit used (see below).
    • A low = $07, B = $08.
    • $04-$06 unchanged.
  • Computation:
    1. a' = (angle + $80) mod $200. Index i = a' & $FF, sign h = bit 8 of a'. Bits 1-7 of $05 are ignored. The +$80 is a quarter turn, which turns sine into cosine.
    2. T = H[i] (0..$FF).
    3. The PPU signed multiply computes P = T × r with r = $06 taken as a signed 8-bit value. Result = bits 8..23 of P as a 16-bit value, i.e. floor(T·r / 256) mod $10000.
    4. If h = 1, two's-complement negate.
  • Tables/data: H is a 256-entry half-period sine, H[i] = sin(π·i/256)·256, clamped to $FF. It equals SMW's 16-bit sine table at $07F7DB (256 words), with the single $0100 entry (i = $80) clamped to $FF. All 256 entries were verified.
  • Side effects: writes $211B twice (T, then 0) and $211C (r). These are the Mode 7 matrix A/B registers and the Mode 7 write latch. This is observable if Mode 7 is in use. SA-1 uses its multiplier with r taken as unsigned, so the results differ for r ≥ $80.
  • Equivalent SMW code: none as a routine. The table data is SMW's, as above.
  • Calls: none.
  • Edge cases: radius $80-$FF produces a negative/garbled magnitude on non-SA-1 (signed multiplier).

CircleY

Computes radius · sin(angle). The contract is the same as CircleX, with these differences:

  • No quarter-turn offset: i = $04, h = $05 bit 0.
  • Output goes to $09-$0A. A low = $09, B = $0A, C = h.
  • $07-$08 are untouched.
  • Same table, same multiply, same side effects.

ExtendedCapeClipping

Checks whether extended sprite X is touching the cape, using a box the caller supplies.

  • Called with:

    • $00 = X offset, $01 = width, $02 = Y offset, $03 = height.
    • DB must map WRAM.
  • Returns:

ExtendedGetDrawInfo

Finds the OAM slot for extended sprite X and the sprite's screen position. Erases or hides the sprite when it is off screen.

  • Called with:
    • 8/8, X = extended slot. 0..7 only.
    • DB must map WRAM.
  • Returns:
    • Y = OAM index for slot X, into the $0200 page, not $0300.
    • $00 = $40 if $1747,x (X speed) bit 7 is clear, else $00. This is the OAM X-flip bit.
    • $01 = low byte of (X − $1A).
    • $02 = low byte of (Y − $1C), or $F0 when the sprite is hidden or erased.
    • X preserved. No stack tricks: the caller must test the outcome itself ($170B,x = 0 or $02 = $F0).
  • Rules:
    • X axis: if the high byte of the 16-bit X − camX ≠ 0, then erase: $170B,x = 0 and $02 = $F0.
    • Y axis: let d = (Ylo − camYlo) mod 256 and c = 1 if Ylo ≥ camYlo. Let t = (Yhi + camYhi + c) mod 256. Note the addition: this is not SMW's test.
      • t ≠ 0: erase if d ≥ $F0, otherwise visible.
      • t = 0: erase if d < $C0; else hide ($02 = $F0, not erased) if d < $E0; else visible.
  • Registers on return:
    • Visible with t ≠ 0: A = d, C = 0.
    • Visible with t = 0: A = d, C = 1.
    • Hidden or erased: A = $F0, N = 1, Z = 0.
  • Tables/data: the OAM index per slot is SMW's 8-byte table at $02A153 ($90,$94,…,$AC).
  • Equivalent SMW code: SMW's extended-sprite draw prologue at $02A1A4-$02A1D3 (same table, same $00/$01 values, same $170B erase). Differences:
    • SMW erases when the high byte of Y − camY ≠ 0 or relY ≥ $F0. PIXI uses the t rule above and has a "hide without erase" band.
    • PIXI writes no OAM.
  • Calls: none.
  • Edge cases: X = 8 or 9 (fireball slots) reads past the 8-entry table, so Y is whatever follows it in ROM. Callers must not use those slots.

ExtendedHurt

Hurts the player if extended sprite X touches them. Uses a fixed 10×10 box.

  • Called with:
    • 8/8, X = extended slot.
    • DB must map WRAM.
  • Returns:
    • No contact: C=0.
    • Contact: SMW's $02A469 has run (see Behaviour). C, A, Y and N/Z are its by-products.
    • X is preserved: $02A469 preserves it on every path that matters.
    • DB is restored. Scratch $00-$0F per the box routines.
  • Behaviour:
    1. Box A:
      • X = $171F,x/$1733,x + 3.
      • Y = $1715,x/$1729,x + 3.
      • Width and height = $0A.
    2. Box B = SMW's player box $03B664.
    3. If $03B72B reports contact, call $02A469 with DB = $02. That routine:
      • With a star ($1490 ≠ 0): turns the extended sprite into a smoke puff. Unless $170B,x = 4, it first moves the sprite 4 px up-left. Then $170B,x = 1 and $176F,x = 7.
      • Else, riding Yoshi: loses Yoshi (see LoseYoshi, but via $18DF).
      • Else: hurts the player via $00F5B7.
  • Stack / control flow: the RTS-ending $02A469 is reached through the RTL at $02B889.
  • Equivalent SMW code: the tail of SMW's extended-vs-player check at $02A3F6-$02A410 (then $02A469). Differences:
    • PIXI skips the layer test ($13F9 vs $1779,x).
    • PIXI uses a fixed box instead of SMW's per-type box ($02A519).
    • PIXI has no special case for type $0A.
  • Calls: $03B664, $03B72B, $02A469.

ExtendedSpeed

Applies an extended sprite's speed to its position, optionally with gravity.

  • Called with:
    • 8/8, X = extended slot.
    • A = mode: 0 = gravity then Y then X; 1 = Y then X; 2 = X only; 3 = Y only.
    • DB must map WRAM.
  • Returns:
    • Modes 0, 1, 2: X = $15E9 on return, because SMW's X updater reloads it. In extended-sprite code $15E9 holds the current extended index, so in practice X is unchanged.
    • Mode 3: X unchanged.
    • Y = $00 or $FF: the sign of the last speed applied. In modes 0, 1 and 2 that is the X speed; in mode 3 it is the Y speed. SMW's X updater runs the Y updater on the X fields.
    • A ≥ 4: returns immediately with A = A − 3 (8-bit) and changes nothing.
  • Dispatch quirk: mode 0 is selected by the Z flag at entry, not by testing A. The modes after it are selected by decrementing A. A caller that loads A = 0 but arrives with Z=0 gets "A ≥ 4" behaviour (A = $FD, nothing done). A caller arriving with Z=1 and A ≠ 0 gets mode 0. Callers normally load A immediately before the call, so this does not arise.
  • Behaviour:
    • Gravity (mode 0): when $173D,x − $40 has bit 7 set (the CMP/BPL test, not a true signed compare), add 3 to $173D,x. So gravity applies when the Y speed is in $C0-$FF or $00-$3F, and not when it is in $80-$BF (fast upward). There is no cap at exactly $40: $3F becomes $42.
    • Y update: SMW $02B560. 4.4 fixed-point: fraction $1751,x += speed·16; position $1715/$1729,x += sign-extended speed>>4 + carry.
    • X update: SMW $02B554. The same on $1747/$175B/$171F/$1733 (via X + $0A), then X = $15E9.
  • Stack / control flow: both SMW routines end in RTS and are reached through the RTL at $02B889.
  • Equivalent SMW code: $02B554 and $02B560 themselves. The gravity rule matches SMW's inline extended-sprite gravity idiom.
  • Calls: $02B554, $02B560.

FinishOAMWrite

Finalises a sprite's OAM tiles: sets each tile's size bit and hides tiles that are off screen.

  • Called with:
    • 8/8, X = sprite slot.
    • A = number of tiles − 1.
    • Y = size: $00 = 8×8, $02 = 16×16, any value with bit 7 set = keep each tile's existing size bit.
    • The tiles are already written at $0300 + $15EA,x onward, with screen-relative coordinates.
    • DB must map WRAM: $0300/$0460 are accessed absolute with the caller's DB.
  • Returns:
    • X = $15E9. N and Z reflect X. C = 1.
    • Y = $15EA,x + 4·(A+1) mod 256, i.e. one past the last tile.
    • A low = $F0 if the last tile was hidden, else the low byte of that tile's Y check value. B = 0.
  • Scratch:

  • Calls: none.

GetMap16

Reads the Map16 tile number at a level position.

  • Called with:
    • Any widths; the routine saves P.
    • $98-$99 = block Y (16-bit). $9A-$9B = block X (16-bit).
    • $1933 = layer (0 or 1).
    • DB must map WRAM: it reads $1933, $1925 and $13D7 absolute. DB is pushed and pulled but never changed.
  • Returns, valid position:
    • A = tile number: 16-bit if entry M=0; otherwise A = low byte and B = high byte.
    • Y = tile high byte. With 16-bit index on entry, Y = $00hh.
    • P = entry P except that N and Z reflect the restored X. X preserved.
  • Returns, invalid position:
    • A = $FFFF (8-bit entry: A = $FF, B = $FF).
    • Y = $FF/$FFFF matching the entry index width.
    • N=1, Z=0 (from Y). Other flags = entry values. X preserved.
  • Steps:
    1. Save the original coordinates: $0E-$0F = $98-$99, $0C-$0D = $9A-$9B.
    2. Orientation and range check:
      • $0A = $5B, or $5B >> 1 when $1933 ≠ 0. Bit 0 of $0A = "this layer is vertical".
      • If vertical: swap the bytes $99 and $9B in RAM. They are not swapped back.
      • Range check, EXLEVEL, horizontal layer: invalid if the 16-bit $98-$99 ≥ $13D7 (unsigned).
      • Range check, EXLEVEL, vertical layer, and every non-EXLEVEL case: invalid if $99 ≥ 2, using the post-swap $99.
      • There is no check on the screen number ($9B after the swap).
    3. Scratch values. All positions here are post-swap except $0D/$0F:
      • $0B = screen number = $9B.
      • $08-$09 = ($98-$99 & $FFF0) | ($9A >> 4).
      • $06 = $20 | ($1933 ? $10 : 0) | (($0F & 1) << 3) | (($0D & 1) << 2) | (($98 >> 6) & 3).
      • $07 = ((($98 >> 4) & 3) << 6) | (($9A >> 3) & $1E).
      • $06/$07 together form the BG tilemap VRAM word address that ChangeMap16 uses.
    4. Map16 address, a chain of three 16-bit adds. Each add carries in the previous one's carry; the first starts with C=0. In practice every carry is 0.
      1. p1 = word[$00BEA8 + 2·$1933] + 2·$1925
      2. p2 = word[$00:p1] + 3·$0B
      3. addr = word[$00:p2] + $08-$09

This is SMW's own pointer chain: $00BEA8 = {$BDA8, $BDE8, …} → per-level-mode tables → 3-byte per-screen pointers. Only their low 16 bits are used.

  1. Tile = $7F:addr << 8 | $7E:addr.
  • Equivalent SMW code: none as a routine. SMW computes Map16 addresses inline (for example $00C1AC); the pointer tables are SMW's.
  • Calls: none.
  • Edge cases:
    • Callers that reuse $98-$9B after a call on a vertical layer see $99/$9B swapped. A second call without restoring them reads the wrong block.
    • $1933 values other than 0/1 index past the $00BEA8 table.
    • With SA-1, the $40/$41 banks are read instead of $7E/$7F.

Erases sprite X when it has moved too far off screen. A selects the size of the off-screen margin.

  • Called with:
    • M=1, X 8-bit, X = sprite slot.
    • A = margin set. Only bits 0-2 are used:
      • 0-3 select SMW bank 1's X0-X3 margins.
      • 4-7 select bank 3's X0-X3 margins.
    • The routine sets DB to its own bank after the first test, so that bank must map WRAM.
  • Returns:
    • Always: $03 = (A & 7) · 2.
    • If $15A0,x | $186C,x = 0: returns at once with A = 0, Z=1, N=0, C=0. Nothing else is changed.
    • Otherwise DB is restored on every exit, so N and Z reflect the caller's DB byte.
    • X preserved, except under EXLEVEL (see "X under EXLEVEL" below).
    • Y = unchanged, or the margin index, or $161A,x (see "Y on return" below).
    • C: on the erase paths, C = 1 exactly when $14C8,x ≥ 8 and $161A,x = $FF, else 0. On the horizontal-level keep path after the margin test, C = $13 bit 0. On every other path C is a by-product.
    • $00 and $01 are clobbered. On paths that test margins, $01 ends as A & 7 (horizontal) or the parity index (vertical).

    1. Bottom-of-level test.
      • EXLEVEL: erase when any of these hold, where bit 15 means bit 15 of the 16-bit result:
        • bit 15 of (Y16 − $13D7) is clear;
        • bit 15 of ((Y16 − $1C) − $0BF2) is clear;
        • bit 15 of ((Y16 − $1C) − $0BF0) is set.

  • Non-EXLEVEL: erase when (Yhi + carry(Ylo + $50) − 2) has bit 7 clear.
  1. If $167A,x bit 2 is set (process while off screen): return.
  2. Margin test:
    • i = (A&7)·2 + ($13 & 1).
    • D = high byte of ($1A16 + sext16(off[i]) − X16), where off = t15[i]:t14[i].
    • If $13 bit 0 is set, D ^= $80.
    • Erase if D bit 7 is set, otherwise return.

The effect: on even frames, test the right margin (erase if the sprite is beyond it); on odd frames, test the left margin.

  • Vertical level:
    1. If $167A,x bit 2 is set, or $13 is odd: return.
    2. If $14E0,x ≥ 2: erase.
    3. j = ($13 >> 1) & 1. D = high byte of ($1C16 + (t13[j]:t12[j]) − Y16). If j = 1, D ^= $80. Erase if D bit 7 is set.
  • Erase:
    1. If $14C8,x ≥ 8 and $161A,x ≠ $FF: sprite load table[$161A,x] = 0. The table is at $7FAF00 (or $1938 when PIXI is built with !Disable255SpritesPerLevel; SA-1: $418A00). This lets the sprite reload.
    2. $14C8,x = 0.
  • Y on return: unchanged, the margin index i/j, or $161A,x on the reload-clearing erase.
  • X under EXLEVEL: in the bottom-of-level test, X is temporarily used and then reloaded from $15E9, so X = $15E9 afterwards. B is restored.
  • Tables/data: all SMW's own.
    • Vertical: t12 = $40,$B0 and t13 = $01,$FF (SMW $01AC0D/$01AC0F, the same at $03B83B).
    • Horizontal, 16 entries: entries 0-7 = SMW $01AC11 (t14) / $01AC19 (t15); entries 8-15 = SMW $03B83F / $03B847.
  • Equivalent SMW code:
    • A=0..3 ≈ $01AC31 / $01AC2B / $01AC27 / $01AC21.
    • A=4..7 ≈ $03B85D / $03B857 / $03B853 / $03B84F.

Differences from bank 1:

  • There is no Magikoopa ($9E = $1F) $18C0/$18C1 handling.
  • Sprites $22/$24 are not exempt on vertical odd-half frames.
  • The load table is $7FAF00, not $1938.
  • The EXLEVEL bottom test.
  • The routine is long-called and switches DB itself.
  • Calls: none.

sa1def.asm macros

Clean-room interface contracts for the assembler macros PIXI defines in asm/sa1def.asm, the file every PIXI sprite is assembled with. Same rules as the rest of this file: behaviour only, no PIXI code, no paraphrase of its instructions, no PIXI comments.

  • Date: 2026-10-20
  • Source read: D:\SMW\Projects\.resources\PIXI\asm\sa1def.asm (7 macros) and, for comparison, D:\SMW\Projects\Secret\tools\pixi\asm\sa1def.asm (a newer copy: the same 7 plus invoke_sa1, and it does not first include an optional config.asm).
  • Usage scanned: every .asm under D:\SMW\Projects\*\Sprites\** and D:\SMW\Projects\Secret\tools\pixi\**, routines folders excluded (107 files), for %Name( calls that are not a shared routine (BigEye\Sprites\routines) and not a macro defined in the calling file or its folder's _header.asm.

Defines the macros depend on

  • !SA1 — 1 when the ROM header byte $00FFD5 is $23 (SA-1 map mode), else 0. Set by sa1def.asm.
  • !Base2 — $6000 on SA-1, $0000 on LoROM. Set by sa1def.asm.
  • !extra_bits — the extra-bits sprite table, indexed by slot: $7FAB10 (LoROM) / $6040 (SA-1). Set by sa1def.asm through define_sprite_table.
  • !__debug — optional, from the user or the command line; treated as 0 when undefined.

debugmsg(msg)

  • Purpose. Assembly-time trace: tells the user where a piece of code landed.
  • Effect. Emits no bytes. If !__debug is undefined it becomes defined as 0. When !__debug equals 1, the assembler prints a line made of $, the current PC in hex, a space and the text msg. Otherwise nothing is printed.
  • Registers/RAM. None (no code generated).
  • SA-1. Identical.

BES(label) — branch if extra bit set

  • Precondition. M=1 (8-bit A); X = the sprite's slot. On SA-1 the table operand is the absolute $6040,x, so DB must reach I-RAM/BW-RAM there ($00-$3F/$80-$BF); on LoROM it is the long $7FAB10,x and DB does not matter.
  • Effect. Tests bit 2 (value $04) of the sprite's extra-bits byte !extra_bits,x — the "extra bit" Lunar Magic stores per placed sprite. Branches to label when the bit is set, falls through when clear.
  • Leaves. A = $04 when the branch is taken, $00 when it falls through; B, X, Y unchanged. Z clear when taken, set when not; N clear; C and V unchanged. No RAM written.
  • Limits. Short relative branch (±128 bytes): label must be near.
  • SA-1. Same, with the table at $6040,x.

BEC(label) — branch if extra bit clear

  • Exactly as BES with the sense inverted: branches to label when bit 2 of !extra_bits,x is clear (A = $00, Z set), falls through when it is set (A = $04, Z clear).

Between(x, label)

  • Parameters. x is an operand written as it would follow an instruction, normally an immediate such as #$10. The macro also needs "two times x", which the assembler forms by appending *2 to that text (so #$10 gives the immediate $20). label is a near (short-branch) label.
  • Effect. Signed range check on A: falls through when -x <= A < x, branches to label otherwise. In effect: A + x (carry cleared first) is compared, unsigned, with 2*x; the branch is taken when the sum is greater than or equal.
  • Leaves. A = original A + x, wrapped to the register width — A is modified. C set when the branch is taken, clear when it falls through; N and Z from the comparison; V from the addition. X, Y and RAM untouched.
  • Width. Works in whichever width M selects. With an 8-bit A, 2*x must fit in a byte (x ≤ $7F).
  • SA-1. Identical.

invoke_snes(addr)

  • Purpose. Run from SA-1 code to make the SNES CPU execute a routine (work the SA-1 cannot do, such as touching PPU or DMA registers). Relies on the SA-1 Pack (1.10+) SNES-side IRQ handler.
  • Parameters. addr — 24-bit address of a routine for the SNES CPU, ending in RTL.
  • Effect. Stores addr little-endian at $0183 (low), $0184 (high), $0185 (bank); writes $D0 to SA-1 register $2209 (raises the SA-1-to-SNES IRQ with the custom IRQ vector selected); waits until $018A reads non-zero (the SA-1 Pack's handler sets it once the SNES routine has returned); then stores 0 to $018A.
  • Leaves. Assumes M=1. A clobbered; X, Y unchanged; Z set, N clear at exit. RAM $0183-$0185 = addr, $018A = 0.
  • LoROM. Meaningless: on a non-SA-1 ROM it hangs, since nothing sets $018A. Only assemble it inside if !SA1 blocks.

invoke_sa1(label) — newer sa1def only

  • Present only in the Secret\tools\pixi copy. The SNES-side counterpart: makes the SA-1 CPU run label (ending in RTL; DB is not set for it, so it must set its own). Stores the 24-bit label at $3180 (low), $3181 (high), $3182 (bank), then calls, with a near JSR, the SA-1 Pack's call-SA-1 helper at $1E80, which returns once the SA-1 routine has finished. The calling code must run in a bank where $1E80 is that helper ($00-$3F/$80-$BF). Assumes M=1; A clobbered. SA-1 only.

define_sprite_table(name, addr, addr_sa1)

  • Effect. Assembly time only, no bytes: defines !name as addr when !SA1 is 0 and as addr_sa1 when !SA1 is 1. name is used as text: it may be passed quoted and may start with a digit (sa1def.asm itself defines both !7FAB10 and !extra_bits this way, each resolving to $7FAB10 / $6040).
  • Note. !SA1 must be set before it is called. Calling it again for an existing name overwrites it.

define_base2_address(name, addr)

  • Effect. Assembly time only: defines !name as addr when !SA1 is 0, and as addr OR !Base2 (addr | $6000) when !SA1 is 1. Meant for $0100-$1FFF WRAM addresses that the SA-1 build relocates to $6100-$7FFF.

Measured against PIXI's (2026-10-20)

Pipe Dream's routines (src/data/spritedriver/routines, MIT) and its versions of the macros above (in src/data/spritedriver/defines.asm, all but the SA-1 invoke_* ones) were written from this file and SMW's code. The routines were then run against PIXI's own in PixiRoutineTests: thousands of random states each, both on the same vanilla ROM in the CPU interpreter, every register, flag and byte of RAM compared, only what this file calls a by-product masked. Where that disagreed with the contracts above, PIXI's behaviour was measured black-box (inputs varied one at a time, outputs read) and ours made to match. The corrections:

  • SpawnSprite / SpawnSpriteSafe, no free slot: A is whatever the search last read, and Y is where the search stopped: $FF when it started below $80 (always, in practice). Started at $81 or above, the first DEY makes it negative and the search ends there, so Y = start − 1; from $80 exactly it carries on down from $7F.
  • GetDrawInfo, off screen: B = 0.
  • GetMap16 / ChangeMap16: 2 × $1933, 2 × $1925 and 3 × the screen are each taken modulo $100, and the tripling keeps the carry out of its doubling (3 × $80 = $81). Only out-of-range inputs see this. $1926, $1934 and $0C do not count.
  • ChangeMap16: A on return is a by-product.
  • Star: C on return is a by-product (PIXI's is mostly set; it is not in the contract).
  • LoseYoshi: confirmed: with $18E2 = 0 the writes land one below each table.
  • FinishOAMWrite: the size index starts at $15EA,x / 4 and counts one per tile without wrapping with the OAM index, so past OAM $FC it goes on to $0460 + $40 and up.
  • ExtendedHurt: PIXI's runs $02A469 with DB = $00, not $02 as above. The one read there that goes by DB is Yoshi's run-off speed ($A4B3,y), so with PIXI's, Yoshi runs off at a speed read from bank 0. Ours keeps DB = $02, as SMW does: the one deliberate difference. The test keeps the player off Yoshi for this routine.

What the random states had to be kept to, and why, is in the test's setups: real level modes and screens, Map16 pointers into ROM at $0FBE, a short stripe buffer, a data bank below $10. Outside those, SMW's own pointers lead into low RAM, where each routine's own stack sits, and the two differ by construction.

    2. t = $16FF,x >> 4. Mask k = SMW's $02AD9A[t] for t 0..3 ($03,$01,$00,$00): speed $00-$0F moves every 4th frame, $10-$1F every 2nd, $20-$3F every frame. PIXI keeps its own 4-byte copy of these values; for t ≥ 4 (speed ≥ $40) it reads whatever PIXI assembled after that copy, which is not defined. Callers keep the speed below $40 (SpawnScoreGeneric uses $30); a differential test must too.
    3. If $13 & k ≠ 0, stop.
    4. If ($16E7,x − $1C) mod 256 < $00, stop (low bytes and layer 1 only, whatever $1705,x says).
    5. Otherwise decrement the 16-bit $16F9:$16E7,x by 1.
  • Returns: X preserved. N and Z reflect the caller's DB byte (restored last). By path:
    • Stopped at 3: Y = t, A = $13 & k, C = bit 3 of $16FF,x.
    • Stopped at 4: Y = old $16E7,x, A = ($16E7,x − $1C) mod 256, C=0.
    • Moved: Y = A = old $16E7,x, C=1.
  • Equivalent SMW code: $02AE38-$02AE5A with the limit fixed at 4 (C=0 gives exactly that). SMW indexes $02AD9A directly, so its t ≥ 4 reads the next SMW table ($02AD9E).
  • Calls: none.

SpinningCoinGetDrawInfo

Meant to find the OAM slot and screen position of spinning-coin sprite X, erasing it when off the side of the screen. As shipped it compares the wrong camera bytes (see Behaviour). The contract describes what it does, not what it was meant to do.

  • Called with: 8/8, X = spinning-coin slot (0..3). DB must map WRAM.
  • Behaviour:
    1. i = (4 · $17E4,x) mod 256. $02-$03 = word at $001C+i (camera Y), $04-$05 = word at $001A+i (camera X). For layer 1: $02=$1C, $03=$1D, $04=$1A, $05=$1B.
    2. b = 1 if $17D4,x < $02, else 0. h = ($17E8,x − $04 − b) mod 256: the coin's Y high byte minus the camera's X low byte. c = 1 if $17E8,x ≥ $04 + b (no borrow), else 0. If h ≠ 0: return, not drawn and not erased.
    3. d = ($17E0,x − $03 − (1 − c)) mod 256: the coin's X low byte minus the camera's Y high byte, minus a borrow that is 0 unless $17E8,x = 0, $04 = $FF and b = 1. If d ≥ $F8: $17D0,x = 0 (erase) and return, not drawn.
    4. Otherwise drawable.
  • Returns:
    • Not drawn at step 2: C=0, A = h, Z=0, N = bit 7 of h, Y = i.
    • Erased at step 3: C=0, A = d, Y = i, N/Z from comparing d with $F8.
    • Drawable: $00 = d, $01 = ($17D4,x − $02) mod 256, Y = A = SMW $0299E9 + x ($30,$38,$40,$48), C=1, N=0, Z=0.
    • $02-$05 are written on every path. X preserved. The X high byte $17EC,x is never read.
  • Equivalent SMW code: $029A08-$029A3D. SMW stores the camera bytes as $02 = Y lo, $03 = X lo, $04 = Y hi and compares against those; PIXI stores two words ($02-$03 = Y, $04-$05 = X) but compares against the same offsets, hence the mix-up. SMW also starts the X subtraction with no borrow, and erases through its own path at $0299E3.
  • Calls: none.
  • For the differential test: with real camera values h is almost never 0, so the routine almost always returns "not drawn". Random states are needed to reach steps 3 and 4.

MinorExtendedGetDrawInfo

Finds the OAM slot and screen position of minor extended sprite X; erases it when well off screen.

  • Called with: 8/8, X = minor extended slot (0..11). DB must map WRAM.
  • Behaviour:
    1. $01 = ry = ($17FC,x − $1C) mod 256. If ry is in $E0..$EF: erase. Only the low bytes are used; the Y high bytes are never read.
    2. $02 = 0. $00 = low byte of X16 − camX (X16 = $18EA:$1808,x, camX = $1B:$1A). If the high byte of that 16-bit difference is non-zero: when ($00 + $38) mod 256 ≥ $70, erase; otherwise $02 = 1 and carry on. Any non-zero high byte counts, not only ±1 screen.
    3. Drawable.
    4. Erase means $17F0,x = 0 and return, not drawn.
  • Returns:
    • Erased at step 1: C=0, A = (ry + $10) mod 256 ($F0..$FF), Y unchanged. $00 and $02 not written.
    • Erased at step 2: C=0, A = ($00 + $38) mod 256, Y unchanged. $00, $01 and $02 (= 0) written.
    • Drawable: C=1, Y = A = the byte at $028B77 + x, N/Z from it. $00, $01, $02 written.
    • X preserved.
  • Tables/data: SMW's minor-extended OAM table is at $028B78 (12 bytes, $50,$54,…,$78,$7C; SMW reads it at $028C6E and seven other places, never at $028B77). PIXI reads one byte earlier, so slot n gets SMW's index for slot n−1, and slot 0 gets $60 (the byte before the table), the same index as slot 5. In a vanilla or PIXI-patched ROM the bytes $028B77-$028B82 are $60,$50,$54,$58,$5C,$60,$64,$68,$6C,$70,$74,$78. To match PIXI, read $028B77 + x.
  • Equivalent SMW code: none as a routine; SMW's minor extended sprites each have their own draw code.
  • Calls: none.

ClusterGetDrawInfo

MinorExtendedSpeed

Moves minor extended sprite X along one axis.

  • Called with: 8/8, X = minor extended slot, A = mode. Only bits 0-1 count: bit 0 = fast, bit 1 = Y axis. DB must map WRAM.
    • 0: slow X: U($182C,x, $1844,x, $18EA:$1808,x).
    • 1: fast X: $18EA:$1808,x += sext8($182C,x) (whole pixels, no fraction).
    • 2: slow Y: U($1820,x, $1838,x, $1814:$17FC,x).
    • 3: fast Y: $1814:$17FC,x += sext8($1820,x).
  • Returns: every mode: Y = $00 if the speed used is < $80, else $FF; A = the new position high byte; N, Z, V, C from the high-byte add (C = carry out of the 16-bit sum). X preserved.

  • Calls: none.

SpawnClusterGeneric (Spawn/ClusterGeneric.asm)

Spawns a cluster sprite at an origin plus an offset.

  • Called with: 8/8. B = cluster number. $00 = X offset, $01 = Y offset (both signed). $02-$03 = origin X, $04-$05 = origin Y (16-bit). DB must map WRAM.
  • Search: slots 19 down to 0, taking the first with $1892,y = 0.
  • Writes (slot n): $1892,n = B; $1E3E:$1E16,n = [$02-$03] + sext($00); $1E2A:$1E02,n = [$04-$05] + sext($01). Nothing else: no misc tables are cleared.
  • Returns:
    • Success: C=0, Y = n, A = the new $1E2A,n, N/Z/V from its add, B = 0.
    • No free slot: C=1, Y = $FF, A = $1892 (slot 0's number, non-zero), N=1, Z=0, B = entry B. Nothing written.
    • X untouched. $00-$07 unchanged.
  • Equivalent SMW code: none (SMW spawns cluster sprites inline).
  • Calls: none.
  • Edge case: the callers disagree. Every _header.asm %SpawnCluster() macro puts the caller's position in $04-$07, as for the other *Generic spawns. With this routine's layout, that gives the new cluster sprite X = whatever is in $02-$03 and Y = the caller's X. Implement the routine's layout ($02/$04); what the header macros should pass is a separate matter.

PIXI 1.40: changes to the 1.2.x routines

  • Date: 2026-10-20
  • Compared: D:\SMW\Projects\BigEye\Sprites\routines\*.asm (1.2.x, the source of the contracts above) with the 1.40 files of the same macro name in D:\SMW\Projects\Secret\tools\pixi\routines\ (ExtendedX → Extended/X.asm, SpawnX → Spawn/X.asm). Both were reduced to their instructions (comments, label spelling and 1.40's local-label syntax removed, defines resolved) and compared. The two sa1def.asm files give the same values for every define these routines use.

Changed in behaviour: 1 of 27 (ExtendedGetDrawInfo).

ExtendedGetDrawInfo: changed

  • Vertical rule. The 1.2.x rule (t formed by addition) is gone. 1.40 uses the true high byte of the 16-bit Y16 − camY16. With d = (Ylo − camYlo) mod 256 and h = that high byte:
    • h = 0: erase if d ≥ $F0, otherwise visible.
    • h = $FF (up to one screen above): erase if d < $C0; hide ($02 = $F0, not erased) if d < $E0; otherwise visible.
    • any other h: erase.

Registers on return keep the same shape: visible with h = 0: A = d, C=0; visible with h = $FF: A = d, C=1; hidden or erased: A = $F0, N=1, Z=0. The X-axis rule, $00, $01 and the erase ($170B,x = 0) are unchanged.

  • OAM index table. 1.40 reads SMW's $02A153 directly instead of its own copy. Slots 0..7 get the same values. Slots 8 and 9 now get SMW's next bytes, $2C and $2D (defined, but not usable OAM indexes), instead of whatever followed PIXI's copy. Callers still must not use those slots.

Same behaviour, different code

  • Star: the player-side test is now a JSL to the shared SubHorzPos instead of a private copy reached by JSR. Same writes ($0E-$0F, Y) and results; it uses one more byte of stack, and a 1.40 Star needs SubHorzPos inserted too.
  • SpawnExtended: the search start is written as !ExtendedSize − 1, which is 7, as before.
  • ExtendedHurt: the bank-2 RTL address is written as $B888 instead of $B889 − 1. Same value.
  • ChangeMap16, GetMap16, SubOffScreen, Aiming: the !EXLEVEL / !SA1 conditionals are written as comparisons. Both defines are only ever 0 or 1, so the same branch is assembled.

Identical

Aiming, CapeContact, ChangeMap16, CheckForContactAlternate, CircleX, CircleY, ExtendedCapeClipping, ExtendedHurt, ExtendedSpeed, FinishOAMWrite, FireballContact, GetDrawInfo, GetMap16, LoseYoshi, Random, SetPlayerClippingAlternate, SetSpriteClippingAlternate, ShooterMain, SpawnExtended, SpawnSmoke, SpawnSprite, SpawnSpriteSafe, Star, SubHorzPos, SubOffScreen and SubVertPos behave the same (only labels, comments, layout and the spellings noted above differ). The corrections under "Measured against PIXI's" apply to the 1.40 versions unchanged.

Measured against PIXI 1.40's (2026-10-20)

PixiRoutineTests runs ours against each PIXI version on the machine that has the routine: 1.2.x (BigEye's copy) and 1.40 (Secret's). Ours match 1.2.x for 26 routines and 1.40 for all 50 but the deliberate differences below. Corrections to the 1.40 contracts above, found that way and measured black-box:

  • BounceGenericDraw: the property byte is $1901,x ORed with the byte at direct page $64 (SMW's sprite priority), not with the value $64. With RAM cleared it is $1901,x exactly.
  • BounceSetMarioSpeed, BounceSetSpriteSpeed: C is from comparing the X speed with $80, but N and Z are from X (the slot is restored last), not from that compare.
  • BounceSetSpeed: N and Z are from X likewise; C and V from the add.
  • MinorExtendedGetDrawInfo, ClusterGetDrawInfo, erasing: just above the screen, N and Z come from A (the $F0-$FF returned); off a side, from the test against $70.
  • ExtendedGetDrawInfo: erased for being more than a screen above or below, C = 0.

Where ours is deliberately not PIXI 1.40's (each has a test of its own):

  • ExtendedGetDrawInfo is 1.40's, so it is not 1.2.x's (whose vertical test adds the camera's high byte).
  • MinorExtendedGetDrawInfo gives each slot SMW's OAM index ($028B78 + x); PIXI's reads one byte early, so its slot 0 shares slot 5's. Everything else in it matches PIXI's.
  • SpinningCoinGetDrawInfo compares the coin with the camera as SMW's own coins do ($029A08): tested against SMW's coin code itself, which it matches in every trial (drawn, erased or left, and where it is drawn, the same place and OAM index). PIXI's compares the wrong camera bytes and almost never draws.
  • SpawnMinorExtendedGeneric exists: PIXI 1.40's _header.asm files call it, but PIXI ships it only as Spawn/Generic.asm (%SpawnGeneric()). Ours has both names.

Found on the way, in Pipe Dream's build: routines called only from a _header.asm were never inserted (the build scanned only the sprites), and our defines.asm defined %LDE(), which PIXI 1.40's headers define themselves. Both fixed; a sprite using PIXI 1.40's sprites/_header.asm spawn macros now builds against our routines.
