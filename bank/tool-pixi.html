PIXI

PIXI (JackTheSpades' SpriteToolSuperDelux, current release 1.43) inserts custom sprites into a Super Mario World ROM. It reads a list of sprites and their configs, assembles each sprite with Asar, inserts a sprite driver and a set of shared routines, writes the tables the driver reads, hooks SMW's sprite code, re-encodes levels whose sprite records change length, and writes the auxiliary files Lunar Magic uses to show the sprites in its editor.

This page describes what PIXI puts in the ROM, its file formats and its behaviour, and gives interface contracts for its shared routines. All addresses are SNES LoROM addresses, written as $BBAAAA. Format facts come from PIXI's README and source tree (master 734b8ed), from PIXI-built ROMs, and from runs in Mesen. [MEASURED] marks a fact measured on an emulator run or by differential testing against PIXI's own code. [LM-DOC] marks a fact from Lunar Magic's help, restated rather than quoted. Untagged facts are read from PIXI's documentation, its output or the SMW disassembly.

PIXI is licensed GPL-3.0 (the root LICENSE covers asm/ and routines/). A clean-room MIT reimplementation of the driver and these routines exists in Pipe Dream; nothing on this page is PIXI code.

What PIXI is

  • The whole tool, in prose: PIXI's README.md is the single best document; it is long and dense.
  • Sprite configs: the .cfg and .json sections of the README, src/cfg.cpp, src/json.cpp. JSON is the modern format. PIXI's C# CFG Editor (src/CFG Editor/) edits configs and converts between the two formats.
  • Lunar Magic aux files: src/lmdata.cpp, src/iohandler.h.
  • Sprite-data remapping (re-encoding levels): src/MeiMei/.
  • The insertion pipeline: src/sprite.cpp, patch_sprites_all_in_one() and patch_sprite().
  • PIXI bundles Asar v1.91 through CMake FetchContent and links it as a library.
  • It also exposes a library API with C, C++, C# and Python bindings, and a C-ABI plugin system.

What PIXI does

  1. Reads the list (list.txt). Entries are NN file for a global sprite and LLL:NN file for a per-level one (B0-BF only). The list is grouped by section headlines (SPRITE:, CLUSTER:, EXTENDED: and the misc kinds). In SPRITE:, slots below C0 read from sprites/, C0-CF from shooters/ and D0 and up from generators/. Only C0-DF run as custom shooters and generators.
  2. Reads each sprite's config (.cfg or .json, below).
  3. Assembles each sprite with Asar. A wrapper gives it the SA-1 and base defines, the shared routines as %Name() macros, its folder's _header.asm, then freecode and the sprite itself. The sprite reports its entry points with Asar prints (print "INIT ",pc, print "MAIN ",pc), and its status entry points (CARRIABLE, KICKED, CARRIED, MOUTH, GOAL) the same way.
  4. Inserts the routines once. Each shared routine a sprite uses goes into freespace once, and its address is kept in a table, so every sprite's macro JSLs the same copy.
  5. Writes the tables: the STSD header, the sprite table, per-level tables, the status pointers and Lunar Magic's sprite size table.
  6. Hooks the game (below).
  7. Fixes the levels whose sprite records changed length (MeiMei). A level's sprite list is walked with the size table, so every level using a number whose record length changed must be re-encoded, not only the levels being edited.
  8. Writes Lunar Magic's aux files (.ssc, .mwt, .mw2, .s16) so LM shows the sprites.

Before inserting, PIXI checks that the ROM has Lunar Magic's VRAM patch ($00F6E4 = $5C) and at least one level saved in LM ($06F624). It refuses a ROM that a newer PIXI version has patched. Sprites may carry VERG checks against the version the driver reports.

A sprite placed in a level is custom when the extra bit $08 of its level-data record is set. A custom sprite shares its number with SMW's sprite of the same number; the extra bit tells them apart.

Cluster and extended sprites

These are ASM alone, with no config and MAIN-only pointer tables. Each must print MAIN. An extended sprite may also print CAPE; without one, cape interaction does nothing (README).

The sprite, or whatever spawns it, stores the custom number itself: the list number plus an offset, in $1892 (cluster) or $170B (extended). The offsets are SMW's own table sizes, read off its dispatchers:

Bit 7 of a cluster number is its extra bit. The minor-kind offsets come from PIXI's asm/sa1def.asm. Its spawn routines (routines/Spawn/*Generic) store the number they are given, so the caller adds the offset. !ExtendedSize is $08 (!ExSprSize+1): spawning keeps off extended slots 8-9, which are Mario's fireballs. Cluster speed tables are named !cluster_misc_1e52 and so on, by address. !Bank8 is $80.

The README names the misc sections and folders and nothing more: not their entry points, registers or how the number is stored.

Apart from each kind's dispatch, SMW reads these number tables only to look for a free slot or to compare with a fixed number, with one exception: the cape's check of extended sprites at $029636, whose clipping ($02A519) is a table indexed by number. That is where an extended sprite's CAPE matters. Extended sprites' timer $176F counts down in SMW's loop before dispatch.

What PIXI puts in the ROM

The STSD header

At $02FFE2: the ASCII tag "STSD", a version byte, flags, a dl pointer to the sprite table, the per-level pointers and the status pointers. The version byte reads 140 on a ROM built by PIXI 1.40.

The sprite table

0x100 entries of 0x10 bytes each, one per sprite number:

offsetsizefield
01type (0 tweak, 1 custom, 2 shooter/generator)
11acts-like
26the six tweaker bytes, in the order $1656 $1662 $166E $167A $1686 $190F
83INIT pointer (24-bit)
113MAIN pointer (24-bit)
142extra property bytes 1 and 2

An empty entry points at $018021, an RTL. Per-level tables (B0-BF) are keyed by the level number in $010B. PIXI writes $010B from $05D8B9.

Lunar Magic's sprite size table

$0EF30C: dl Size : db $42 points at a 0x400-byte table that gives 3 + count bytes per (extra bits, number), where count is the sprite's extra-byte count. The game's sprite loader steps through a level's sprite list with it. The size table is per number, not per level: if any level has its own B0-BF sprite, B0-BF records are the longer length in every level.

Status pointers

A sprite may print CARRIABLE (status 09), KICKED (0A), CARRIED (0B), MOUTH (07) and GOAL (0C). The printed code then runs in that status in place of SMW's, and a status it does not print runs SMW's code as before. The second extra property byte overrides this: bit 7 runs MAIN instead, bit 6 runs MAIN first (then the sprite's entry, or SMW's).

The load table move (255 sprites per level)

SMW's load table $1938 holds one byte per record of the level's sprite list, indexed by $161A,x. A set byte means "spawned, do not spawn again". It is 128 bytes, so a 129th record writes into the screen exits at $19B8. Since PIXI 1.2.15 (its changelog) the table is moved to $7FAF00, 256 bytes; !1938 names it, and index FF still means "not from the level". Since PIXI 1.41, !1938 is always the remapped $7FAF00 and disabling the remap (!Disable255SpritesPerLevel) is an error.

Every SMW instruction that addresses $1938 (found by scanning for each absolute opcode with that operand; no long forms exist, and three hits in bank 0D are tile data) [MEASURED]:

  • $02A856: the loader's test-and-mark.
  • $02ABF2: the level-load clear. It is 64 bytes in SMW and 128 after Lunar Magic changes $02ABF3 to $7F.
  • $02A8BB: a generator's record, left unmarked.
  • $02A936: no free slot.
  • $02FAE6: indexed by $0FBC,y.
  • Six LDA #$00 : STA $1938,y that free a record: $01AC9C (the off-screen erase), $02AB99 (a shooter's), $02D088, $02FF15, $038712, $03B8BA.

Lunar Magic's bank-1E loader never touches $1938, and jumps back only to $02A846, $02A84B and $02A856.

Lunar Magic is told the limit is 255 by clearing bit 0 of $0FFFE0. LM's help ("Custom Sprite List Sizes") gives this as PC offset 0x801E0; LM's PC offsets count the 0x200-byte copier header (its 0x7750C is the $0EF30C size-table pointer) [LM-DOC]. Every PIXI ROM examined has $FE there; an LM-saved hack without PIXI has $FF.

Notes on these hooks [MEASURED]:

  • On LM-saved ROMs, $02A846 is already Lunar Magic's record step (JML into LM's bank-1E code: INX : INY : INY, then a BPL that rebases $CE past $80), fixed at 3 bytes. Nothing in the game reads the size table until a driver hooks this. SMW's own loader continues at $02A82E.

  • Asar 1.91 assembles BNE $02A846 (an absolute operand) as a branch offset of $46. Branch to a label, or use JML.

Config formats

list.txt

NN file for a global sprite, LLL:NN file for a per-level one, under section headlines (SPRITE:, CLUSTER:, EXTENDED:, then the misc kinds by name). A misc kind's section name is its folder name under misc_sprites/.

CFG

Six lines:

  1. type: 0 tweak, 1 custom, 2 shooter/generator;
  2. acts-like;
  3. the six tweaker bytes $1656 $1662 $166E $167A $1686 $190F;
  4. extra property bytes 1 and 2;
  5. the ASM file;
  6. a:b extra-byte counts (extra bit clear : extra bit set), in hex, at most 0C.

JSON

The same fields, with these differences:

  • Each tweaker byte is an object of named fields. src/json_const.h has the exact names, typos included (for example "Don't disable cliping when starkilled").
  • The extra-byte counts are in decimal.
  • Map16: base64, 8 bytes per 16×16 tile, the TL, BL, TR, BR tile words. A Map16 value that is not base64 reads as no tiles.
  • DisplayType: XY or ExByte.
  • Displays: each entry has a description, the extra bit, and either a position nibble X/Y (0-F) or an extension byte Index/Value; then either text or Tiles, each tile a signed pixel offset and a Map16 tile number.
  • Collection: entries of name, extra bit and up to 12 extra-byte values. This is Lunar Magic's sprite list ("Add Sprites").

Extra data: five different things

These are easy to confuse:

  • tweak bytes: the six tweaker bytes of the table entry;
  • extra property bytes: two config bytes copied into the table entry;
  • extra bytes: per-placement bytes in the level's sprite record, counted in the size table;
  • shooter extra bytes: the same for shooters;
  • the indirect data pointer: exists because Lunar Magic caps per-sprite data at 12 bytes.

The extra bit lives in bit 2 (value $04) of the sprite's !extra_bits,x byte at runtime ($7FAB10,x on LoROM, $6040,x on SA-1).

Display tiles

Display tiles are numbered in Lunar Magic's sprite Map16, 0x000-0x3FF. A sprite's own Map16 replaces tiles from 0x300. Most real configs use LM's own tiles (0x030 is the green shell; 0x006, 0x007, ...). LM's table sits uncompressed in Lunar Magic.exe: 0x400 tiles × 8 bytes. Tile words use FG Map16's layout, YXPCCCTT TTTTTTTT. 8×8 tiles 0x000-0x1FF are SP1-SP4 and 0x200-0x2FF are GFX33 (Yoshi is 0x080-0x0A3). LM 3.21's copy, as PIXI's CFG Editor++ embeds it in an LM16 export, differs from LM 3.40's in two tiles (16F and 21B) and stops at 0x2FF.

Files PIXI writes for Lunar Magic

PIXI writes <rom>.ssc (tooltips and display), .mwt (list names), .mw2 (list data) and .s16 (sprite Map16) beside the ROM, from the global slots' JSON configs. The formats are in Lunar Magic's help ("Custom Tooltips for Sprites", "Custom Collections of Sprites", "Custom Map16 for Sprites") [LM-DOC]. These details are as PIXI writes them, where the help is silent [MEASURED]:

  • .ssc fields are space-separated (the help says tab; LM reads both). Lines end CRLF.
  • .mwt is tab-separated, CRLF, with the sprite number only on a sprite's first entry.
  • The .ssc TYPE field is the Y nibble, the X nibble, then 20/30 (extra bit clear/set) plus 0 for a description, 2 for tiles or 8 for GFX files. For a display chosen by extension byte it is the byte's number counting the three record bytes (Index + 3), two hex digits of value, then the same. Tile numbers and GFX files are written in hex.
  • .mw2 starts with a 00 header and ends with FF. Each record is 70|extra<<2|1, 70, number, bytes.... Every record sets the "next group" flag, so each Collection entry is its own list item.
  • .s16 starts at sprite tile 0x400. PIXI 1.43 writes 0x10 pages (LM itself saves 0x38). PIXI 1.40 writes the same content zero-padded to 0x1C000 bytes. Each sprite's own tiles go in slot order, and its display tiles from 0x300 are renumbered to match.
  • PIXI writes nothing for a .cfg sprite.

PIXI does not write the overworld's .sscov/.s16ov.

Known bugs and quirks

  • .ssc line breaks: a description containing a line break is written raw into the .ssc, ending the line mid-text. LM's escape is \n [MEASURED].
  • .mw2 stale bytes: extra bytes past a Collection entry's fourth are filled from stale memory (one observed .mw2 held the bytes of "tra", "By", "Ext") [MEASURED].
  • .cfg sprites: get no aux-file entries at all.
  • ExtendedHurt runs SMW's $02A469 with DB = $00. SMW runs it with DB = $02. The one DB-relative read there is Yoshi's run-off speed ($A4B3,y), which therefore comes from bank 0 [MEASURED].
  • MinorExtendedGetDrawInfo reads SMW's OAM table one byte early, so slot n gets slot n−1's index and slot 0 shares slot 5's [MEASURED].
  • SpinningCoinGetDrawInfo compares the coin's position with the wrong camera bytes, and almost never draws [MEASURED].
  • SpawnClusterGeneric expects the origin in $02-$05; every _header.asm %SpawnCluster() macro passes it in $04-$07.
  • SpawnMinorExtendedGeneric is called by every 1.40 _header.asm but does not exist: the file is Spawn/Generic.asm, so its macro is %SpawnGeneric().
  • ScoreUpdateYPos reads past its 4-byte table for speeds $40 and up.
  • ExtendedGetDrawInfo on slots 8 and 9 reads past its 8-entry table.
  • LoseYoshi takes Yoshi's slot from $18E2; SMW uses $18DF.
  • SubHorzPos writes the low byte of the difference to $0E and the high byte to $0F. SMW's version writes the low byte to $0F.
  • Map16 not base64: a config whose Map16 is not base64 (one observed config holds the text "Cape Shell") reads as no tiles rather than an error.

Shared routines

These are interface contracts for PIXI's shared sprite routines: each is inserted once and called with JSL through %Name(). They are written from the routines' observable behaviour. Each contract says what a caller can see: inputs, outputs, RAM written, flags, stack effects and edge cases. They hold no PIXI code: no instruction sequences, no instruction-by-instruction paraphrase, no PIXI comments and no PIXI data tables. A table is described only when it is SMW's own (its address is cited) or when it can be defined by a formula. SMW addresses were checked against a vanilla ROM.

The contracts were checked by running an independent implementation against PIXI's own routines from thousands of random states each, on the same vanilla ROM in a CPU interpreter, comparing every register, flag and byte of RAM with only what is called a by-product here masked. Where that disagreed with a contract, PIXI was measured black-box (inputs varied one at a time, outputs read) and the contract corrected; corrected points are marked [MEASURED]. The random states were kept to real level modes and screens, Map16 pointers into ROM at $0FBE, a short stripe buffer and a data bank below $10; outside those, SMW's own pointers lead into low RAM.

Conventions that apply to every routine

  • Build. The contracts describe the LoROM, non-SA-1 build. RAM is named by its SMW address: sprite tables are $E4,x, $14E0,x, etc.; "slot" means a normal-sprite slot 0..$0B. The SA-1 build moves the sprite tables (!addr = $6000 and so on), uses the SA-1 arithmetic unit instead of $4202/$211B, and uses $40/$41 instead of $7E/$7F for Map16. These differences are noted briefly where they apply.
  • Returning. Every routine is entered with JSL and returns with RTL, unless "Stack" says otherwise.
  • Direct page. D = $0000 is assumed: $00-$FF is RAM $7E:0000-00FF.
  • Data bank. "DB must map WRAM" means DB must be a bank where $0000-$1FFF mirrors low WRAM ($00-$3F or $80-$BF). Every routine that reads a sprite table with absolute addressing needs this.
  • Widths. "8/8" means the routine expects M=1 (8-bit A) and X=1 (8-bit X/Y) on entry. Most of them do. When a routine runs with the wrong widths, its immediate operands shift and the result is garbage, so treat 8/8 as a hard precondition unless the contract says otherwise.
  • B. The high byte of the accumulator, which XBA exposes. It is listed only where it is deterministic and might be relied on. Otherwise it is a by-product.
  • Flags. Any flag not listed under Returns is a by-product. V is a by-product everywhere. A differential test should mask by-product flags. Flags that are listed are exact.
  • EXLEVEL. PIXI decides at assembly time whether Lunar Magic's tall-level support is present (!EXLEVEL). It reads the Lunar Magic version string at ROM $0FF0B4; versions above 2.53 set it. Every ROM saved by Lunar Magic 3.x takes the EXLEVEL branch, so that branch is the one that matters for current ROMs. SubOffScreen, GetMap16 and ChangeMap16 behave differently depending on this flag.
  • SMW routines called. These belong to the ROM, not to PIXI. A reimplementation may call the same addresses:
    • $01ACF9: random number generator.
    • $02A9DE: find a free slot, keeping 2 slots in reserve.
    • $03B664: player clipping, box B.
    • $03B69F: sprite clipping, box A.
    • $03B72B: box-vs-box contact test; returns C.
    • $07F7D2: initialise a slot's tables.
    • $0187A7: give a slot its custom tables. This address is PIXI's driver hook, not vanilla SMW code.
    • $02ACE5: give points.
    • $01AB6F: contact sound and contact graphic.
    • $02A469: extended sprite hurts the player.
    • $02B554/$02B560: extended sprite X/Y speed. These end in RTS.
    • $00C0FB: queue a Map16 tile to VRAM. Ends in RTS.

PIXI reaches the RTS-ending routines ($02B554/$02B560, $00C0FB) from another bank with the usual "push a long return address, then push the address of an RTL in the target bank minus 1" trick. The RTL bytes it uses are at $00804D and $02B889. Any equivalent call mechanism is acceptable.

  • Box layout used by SMW's contact test $03B72B. Box A is $04 x-low, $0A x-high, $05 y-low, $0B y-high, $06 width, $07 height. Box B is $00, $08, $01, $09, $02, $03 in the same order. $03B72B preserves X and Y, clobbers $0C and $0F, and returns C=1 on contact.

Aiming

Computes an 8-bit X speed and Y speed of magnitude about speed, pointing from the shooter toward the target.

  • Called with:
    • Any register widths. The routine saves P and sets 8/8 itself.
    • A (low byte) = speed s, unsigned.
    • $00-$01 = 16-bit dx = shooter X − target X.
    • $02-$03 = 16-bit dy = shooter Y − target Y.
    • DB is irrelevant.
  • Returns:
    • $00 = X speed (8-bit). $02 = Y speed (8-bit). $01 = $03 = 0.
    • Each output is the value computed below, not negated when its input d had bit 15 set (target to the right / below), and two's-complement negated when bit 15 was clear. d = 0 gives a negated 0, which is 0.
    • P is restored exactly as on entry, so widths and C/V/D/I are the entry values, except that N and Z reflect the restored X.
    • X is preserved. Y is untouched.
    • A low byte = the final $00. B = high byte of the 16-bit Vx below.
  • Scratch RAM: $04-$05 = S (16-bit, defined below). $06 = 1 if dx was negative, otherwise 0. $07 = 0. $0F = s. The multiplier registers $4202/$4203/$4216/$4217 are left holding the last product.
  • Algorithm:
    1. Take absolute values: two's-complement negate dx or dy if bit 15 is set. $8000 stays $8000 and is then treated as unsigned.
    2. While (|dx| OR |dy|) ≥ $100, shift both right by 1. The shift count is the bit-length of the high byte of the OR. After this, ax, ay ≤ $FF.
    3. d = ax² + ay², a 17-bit unsigned value.
    4. Choose sh as the smallest value in 0..5 with d >> (2·sh) < $100. The six bands are d < $100, < $400, < $1000, < $4000, < $10000, and ≥ $10000. Then k = d >> (2·sh) and m = R[k] >> sh (16-bit logical shift).
    5. S = floor(s · m / 256). This is exact and always fits in 16 bits.
    6. Vy = floor(ay · S / 256) and Vx = floor(ax · S / 256), both 16-bit. The outputs are their low bytes, sign-applied as above.
  • Tables/data: R is a 256-entry table of 16-bit words: R[0] = $FFFF, and R[k] = min($FFFF, round(65536 / √k)) for k ≥ 1. All 256 entries were checked against this formula. SMW has no such table. m approximates 65536/√d, so S·a/256 ≈ s·a/√d.
  • Stack / control flow: normal.
  • Equivalent SMW code: none. (SMW's aimed projectiles use other methods.)
  • Calls: none. Uses the hardware multiplier at $4202/$4203 (SA-1: $2250-$2254/$2306-$2307). Allow 8 cycles before each product read.
  • Edge cases:
    • dx = dy = 0 gives 0, 0.
    • d = 1 uses R[1] = $FFFF.
    • The magnitude can slightly exceed s because of rounding. Only the low byte is kept, so s close to $FF can wrap.
    • The SA-1 build computes m·s through the SA-1 multiplier with a different path for m ≥ $8000. Its results are the same in intent but not guaranteed to be bit-identical, and this contract does not cover them.

CapeContact

Checks whether sprite X is touching the spinning cape.

  • Called with:
    • 8/8, X = sprite slot.
    • DB must map WRAM.
  • Returns:
    • C=1 for contact, C=0 for none. X and Y are preserved.
  • RAM written / scratch: when the box test runs: $00-$0B (both boxes), plus $0C and $0F (from $03B72B). The early "no" exits write nothing.
  • Behaviour: returns C=0 without touching RAM if any of these holds:
    • $13E8 (cape-spin active) = 0.
    • $15D0,x | $154C,x | $1FE2,x ≠ 0.
    • Layer mismatch: let L = $1632,x, with bit 0 flipped when $74 (climbing) ≠ 0. Exit if L ≠ $13F9, comparing the whole byte.

Otherwise:

  1. Box A comes from SMW's $03B69F.
  2. Box B is the cape box:
    • X = 16-bit ($13E9/$13EA) − 2, giving $00/$08. Width $14 in $02.
    • Y = $13EB/$13EC, giving $01/$09. Height $10 in $03.
  3. The result is $03B72B's.
  • Stack / control flow: the final step is a tail jump into $03B72B, so $03B72B's RTL returns to the caller.
  • Equivalent SMW code: the per-sprite body of SMW's cape-vs-sprite check, $0293CE-$0293F2. The cape box is SMW's $029696 exactly. Differences:

CircleX

Computes radius · cos(angle).

  • Called with:
    • 8/8.
    • $04-$05 = angle. Only 9 bits count: $05 bit 0 and $04, with $000-$1FF = 0–360°.
    • $06 = radius.
  • Returns:
    • $07-$08 = 16-bit signed X displacement.
    • M=1.
    • X preserved (N and Z reflect X).
    • C = the half-circle sign bit used (see below).
    • A low = $07, B = $08.
    • $04-$06 unchanged.
  • Computation:
    1. a' = (angle + $80) mod $200. Index i = a' & $FF, sign h = bit 8 of a'. Bits 1-7 of $05 are ignored. The +$80 is a quarter turn, which turns sine into cosine.
    2. T = H[i] (0..$FF).
    3. The PPU signed multiply computes P = T × r with r = $06 taken as a signed 8-bit value. Result = bits 8..23 of P as a 16-bit value, i.e. floor(T·r / 256) mod $10000.
    4. If h = 1, two's-complement negate.
  • Tables/data: H is a 256-entry half-period sine, H[i] = sin(π·i/256)·256, clamped to $FF. It equals SMW's 16-bit sine table at $07F7DB (256 words), with the single $0100 entry (i = $80) clamped to $FF. All 256 entries were verified.
  • Side effects: writes $211B twice (T, then 0) and $211C (r). These are the Mode 7 matrix A/B registers and the Mode 7 write latch. This is observable if Mode 7 is in use. SA-1 uses its multiplier with r taken as unsigned, so the results differ for r ≥ $80.
  • Equivalent SMW code: none as a routine. The table data is SMW's, as above.
  • Calls: none.
  • Edge cases: radius $80-$FF produces a negative/garbled magnitude on non-SA-1 (signed multiplier).

GetMap16

Reads the Map16 tile number at a level position.

  • Called with:
    • Any widths; the routine saves P.
    • $98-$99 = block Y (16-bit). $9A-$9B = block X (16-bit).
    • $1933 = layer (0 or 1).
    • DB must map WRAM: it reads $1933, $1925 and $13D7 absolute. DB is pushed and pulled but never changed.
  • Returns, valid position:
    • A = tile number: 16-bit if entry M=0; otherwise A = low byte and B = high byte.
    • Y = tile high byte. With 16-bit index on entry, Y = $00hh.
    • P = entry P except that N and Z reflect the restored X. X preserved.
  • Returns, invalid position:
    • A = $FFFF (8-bit entry: A = $FF, B = $FF).
    • Y = $FF/$FFFF matching the entry index width.
    • N=1, Z=0 (from Y). Other flags = entry values. X preserved.
  • Steps:
    1. Save the original coordinates: $0E-$0F = $98-$99, $0C-$0D = $9A-$9B.
    2. Orientation and range check:
      • $0A = $5B, or $5B >> 1 when $1933 ≠ 0. Bit 0 of $0A = "this layer is vertical".
      • If vertical: swap the bytes $99 and $9B in RAM. They are not swapped back.
      • Range check, EXLEVEL, horizontal layer: invalid if the 16-bit $98-$99 ≥ $13D7 (unsigned).
      • Range check, EXLEVEL, vertical layer, and every non-EXLEVEL case: invalid if $99 ≥ 2, using the post-swap $99.
      • There is no check on the screen number ($9B after the swap).
    3. Scratch values. All positions here are post-swap except $0D/$0F:
      • $0B = screen number = $9B.
      • $08-$09 = ($98-$99 & $FFF0) | ($9A >> 4).
      • $06 = $20 | ($1933 ? $10 : 0) | (($0F & 1) << 3) | (($0D & 1) << 2) | (($98 >> 6) & 3).
      • $07 = ((($98 >> 4) & 3) << 6) | (($9A >> 3) & $1E).
      • $06/$07 together form the BG tilemap VRAM word address that ChangeMap16 uses.
    4. Map16 address, a chain of three 16-bit adds. Each add carries in the previous one's carry; the first starts with C=0. In practice every carry is 0.
      1. p1 = word[$00BEA8 + 2·$1933] + 2·$1925
      2. p2 = word[$00:p1] + 3·$0B
      3. addr = word[$00:p2] + $08-$09

This is SMW's own pointer chain: $00BEA8 = {$BDA8, $BDE8, …} → per-level-mode tables → 3-byte per-screen pointers. Only their low 16 bits are used. 2 × $1933, 2 × $1925 and 3 × the screen are each taken modulo $100, and the tripling keeps the carry out of its doubling (3 × $80 = $81); only out-of-range inputs see this. $1926, $1934 and $0C do not count [MEASURED].

  1. Tile = $7F:addr << 8 | $7E:addr.
  • Equivalent SMW code: none as a routine. SMW computes Map16 addresses inline (for example $00C1AC); the pointer tables are SMW's.
  • Calls: none.
  • Edge cases:
    • Callers that reuse $98-$9B after a call on a vertical layer see $99/$9B swapped. A second call without restoring them reads the wrong block.
    • $1933 values other than 0/1 index past the $00BEA8 table.
    • With SA-1, the $40/$41 banks are read instead of $7E/$7F.

ShooterMain

Decides whether shooter X fires this frame and finds a free sprite slot for the shot.

  • Called with:
    • 8/8, X = shooter slot (0..7).
    • A = timer reload value.
    • C=1 to apply the "player is next to the shooter" veto, C=0 to skip it.
    • DB must map WRAM.
  • Returns:
    • C=0 means fire: Y = free slot from $02A9DE, A = Y, N=0, Z = (Y = 0).
    • C=1 means don't fire.

    • B is clobbered. X preserved.

    1. If $17AB,x ≠ 0: stop. The timer is not changed.
    2. $17AB,x = A, whether or not the shooter fires afterwards.

    5. Stop if the high byte of (shooterX − camX) ≠ 0.
    6. Stop if (($179B,x − $1A) + $10) mod 256 < $10, i.e. the shooter is in the rightmost 16 px of the screen.

    • PIXI makes the player veto optional and tests it first. SMW tests it last. There are no side effects between the steps, so the outcome is the same.
  • Calls: $02A9DE. It uses $0E/$0F and searches from the top of the $1692-dependent slot range down, keeping 2 slots in reserve.

SpawnSprite

Spawns a normal or custom sprite at sprite X's position plus an offset, with initial speeds.

  • Called with:
    • 8/8, X = parent slot.
    • A = sprite number.
    • C=1 for a custom sprite, C=0 for a vanilla one.
    • $00 = X offset (signed), $01 = Y offset (signed), $02 = X speed, $03 = Y speed.
    • DB must map WRAM.
  • Returns:
    • Success: C=0, Y = new slot, X = parent. N and Z come from loading $03.
    • Failure (no free slot): C=1, X = parent (N and Z reflect X). A is whatever the search last read. Y is where the search stopped: $FF whenever it started below $80, which is always the case here [MEASURED].
    • $00-$03 are preserved, even across $0187A7.
  • Search: slots $0B down to 0 (SA-1: $15 down to 0), taking the first with $14C8 = 0. All slots are searched: the $1692 sprite-memory limits are ignored.
  • Writes, in order, for slot n:
    1. $9E,n = number.
    2. Call $07F7D2, which clears the slot and loads vanilla tweakers for $9E,n. The carry flag must survive this call; it does in vanilla and in a PIXI-patched ROM.
    3. Custom only:
      1. $7FAB9E,n = number.
      2. Call $0187A7 (the driver's "load custom tables" hook). It clobbers $00-$02; PIXI saves and restores $00-$03 around it.
      3. $7FAB10,n = $08 (custom flag set, extra bits clear).
    4. $14C8,n = 1 (init).
    5. $E4,n/$14E0,n = parent X16 + sext($00).
    6. $D8,n/$14D4,n = parent Y16 + sext($01).
    7. $B6,n = $02, $AA,n = $03.
    8. Nothing else is set: no direction, no layer ($1632), no off-screen flags.
  • Equivalent SMW code: none as a routine. Compare SMW's inline spawns that use $02A9DE/$07F7D2.
  • Calls: $07F7D2, $0187A7 (custom only).
  • Edge cases: for a vanilla spawn, the custom-state cleanup relies on the driver's hook inside $07F7D2 (at $07F785).

SpawnSpriteSafe

The same as SpawnSprite, except that the search starts at slot $04 (caller-supplied) and goes down to 0.

  • Edge cases:
    • $04 must be < the slot count.
    • No free slot [MEASURED]: started below $80, Y = $FF. Started at $81 or above, the first decrement makes Y negative and the search ends there, so Y = start − 1. Started at $80 exactly, the search carries on down from $7F.

Star

Star-kills sprite X and gives the player points, as a star hit does.

  • Called with:
    • 8/8, X = sprite slot.
    • The routine does not check that the player has a star.
  • Returns:
    • X preserved.
    • Y = the sound index used ($18D2 capped to 8).
    • $0E-$0F = 16-bit ($94 − sprite X).
    • DB is preserved: it is set to the routine's own bank internally, so that bank must map WRAM.
    • N and Z come from restoring DB. C is a by-product [MEASURED].
  • Behaviour, in order:
    1. $01AB6F: $1DF9 = $03, plus a contact-graphic smoke when the sprite is on screen.
    2. $14C8,x = 2 and $AA,x = $D0.
    3. $B6,x = $F0 if the player is to the right ($94/$95 ≥ sprite X), else $10. This is SMW's table at $01A839, indexed by the SubHorzPos result.
    4. $18D2 += 1, then capped at 8.
    5. $02ACE5 with A = $18D2: gives points, or a 1-up at 8.
    6. $1DF9 = the sound for $18D2: index 1-7 gives $13-$19, index ≥ 8 gives $03, index 0 gives $00.
  • Equivalent SMW code: the star branch of SMW's sprite-player contact, $01A847-$01A87D. Differences:
    • Order: SMW gives points and sound first and sets the status and speeds afterwards.
    • Direction: SMW uses $D1/$D2 ($01AD30, the player's X at the start of the frame) and writes only $0F. PIXI uses $94/$95 and writes $0E-$0F.
    • Count ≥ 8: SMW leaves $1DF9 as $01AB6F set it ($03). PIXI writes $03 itself, so the result is the same.
    • Count wrapped to 0 ($18D2 was $FF): SMW reads $01A61D ($60); PIXI uses $00.
    • PIXI does not check the $167A bit 1 "immune to star" flag. The caller's code does that.
  • Tables/data: X speeds = SMW $01A839 ($F0,$10). Sounds = SMW $01A61E-$01A624 ($13-$19), plus $00 and $03 as above.
  • Calls: $01AB6F, $02ACE5. In 1.40 the player-side test is a JSL to the shared SubHorzPos, so a 1.40 Star needs SubHorzPos inserted too.

SubHorzPos

Reports which side of sprite X the player is on.

  • Called with:
    • 8/8, X = sprite slot.
  • Returns:
    • $0E-$0F = 16-bit $94/$95 − $E4/$14E0,x: low byte in $0E, high byte in $0F.
    • Y = 1 if that difference is negative (player to the left), else 0.
    • A = high byte of the difference.
    • Y = 0: N=0, Z = (high byte = 0), C = no-borrow of the high-byte subtraction.
    • Y = 1: N=0, Z=0.
  • Equivalent SMW code: $03B817 / $02D4FA. Difference: SMW stores the low byte in $0F and does not write $0E. Sprites written against SMW's convention that read $0F as the low byte get the high byte here. $01AD30 is the variant that uses $D1/$D2.
  • Calls: none.

SubOffScreen

Erases sprite X when it has moved too far off screen. A selects the size of the off-screen margin.

  • Called with:
    • M=1, X 8-bit, X = sprite slot.
    • A = margin set. Only bits 0-2 are used:
      • 0-3 select SMW bank 1's X0-X3 margins.
      • 4-7 select bank 3's X0-X3 margins.
    • The routine sets DB to its own bank after the first test, so that bank must map WRAM.
  • Returns:
    • Always: $03 = (A & 7) · 2.
    • If $15A0,x | $186C,x = 0: returns at once with A = 0, Z=1, N=0, C=0. Nothing else is changed.
    • Otherwise DB is restored on every exit, so N and Z reflect the caller's DB byte.
    • X preserved, except under EXLEVEL (see "X under EXLEVEL" below).
    • Y = unchanged, or the margin index, or $161A,x (see "Y on return" below).
    • C: on the erase paths, C = 1 exactly when $14C8,x ≥ 8 and $161A,x = $FF, else 0. On the horizontal-level keep path after the margin test, C = $13 bit 0. On every other path C is a by-product.
    • $00 and $01 are clobbered. On paths that test margins, $01 ends as A & 7 (horizontal) or the parity index (vertical).
  • Horizontal level ($5B bit 0 = 0):
    1. Bottom-of-level test.
      • EXLEVEL: erase when any of these hold, where bit 15 means bit 15 of the 16-bit result:
        • bit 15 of (Y16 − $13D7) is clear;
        • bit 15 of ((Y16 − $1C) − $0BF2) is clear;
        • bit 15 of ((Y16 − $1C) − $0BF0) is set.

$13D7 = level height. $0BF2 and $0BF0 are the Y range limits kept in RAM.

  • Non-EXLEVEL: erase when (Yhi + carry(Ylo + $50) − 2) has bit 7 clear.
  1. If $167A,x bit 2 is set (process while off screen): return.
  2. Margin test:
    • i = (A&7)·2 + ($13 & 1).
    • D = high byte of ($1A16 + sext16(off[i]) − X16), where off = t15[i]:t14[i].
    • If $13 bit 0 is set, D ^= $80.
    • Erase if D bit 7 is set, otherwise return.

The effect: on even frames, test the right margin (erase if the sprite is beyond it); on odd frames, test the left margin.

  • Vertical level:
    1. If $167A,x bit 2 is set, or $13 is odd: return.
    2. If $14E0,x ≥ 2: erase.
    3. j = ($13 >> 1) & 1. D = high byte of ($1C16 + (t13[j]:t12[j]) − Y16). If j = 1, D ^= $80. Erase if D bit 7 is set.
  • Erase:
    1. If $14C8,x ≥ 8 and $161A,x ≠ $FF: sprite load table[$161A,x] = 0. The table is at $7FAF00 (or $1938 when PIXI is built with !Disable255SpritesPerLevel; SA-1: $418A00). This lets the sprite reload.
    2. $14C8,x = 0.
  • Y on return: unchanged, the margin index i/j, or $161A,x on the reload-clearing erase.
  • X under EXLEVEL: in the bottom-of-level test, X is temporarily used and then reloaded from $15E9, so X = $15E9 afterwards. B is restored.
  • Tables/data: all SMW's own.
    • Vertical: t12 = $40,$B0 and t13 = $01,$FF (SMW $01AC0D/$01AC0F, the same at $03B83B).
    • Horizontal, 16 entries: entries 0-7 = SMW $01AC11 (t14) / $01AC19 (t15); entries 8-15 = SMW $03B83F / $03B847.
  • Equivalent SMW code:
    • A=0..3 ≈ $01AC31 / $01AC2B / $01AC27 / $01AC21.
    • A=4..7 ≈ $03B85D / $03B857 / $03B853 / $03B84F.

Differences from bank 1:

  • There is no Magikoopa ($9E = $1F) $18C0/$18C1 handling.
  • Sprites $22/$24 are not exempt on vertical odd-half frames.
  • The load table is $7FAF00, not $1938.
  • The EXLEVEL bottom test.
  • The routine is long-called and switches DB itself.
  • Calls: none.

Conventions for this section

Everything under "Conventions that apply to every routine" above still holds (LoROM, D = 0, JSL/RTL, 8/8 on entry, by-product flags). In addition:

  • X = the slot of the calling sprite's own kind (bounce slot, score slot, ...), 8-bit. No routine range-checks it. Every sprite table is read with absolute addressing, so DB must map WRAM for every routine in this section. ROM tables ($02xxxx) are read long and do not depend on DB.
  • RAM per sprite kind (LoROM; the SA-1 build ORs $6000 into each, as define_base2_address does):

| kind | slots | number | X lo/hi | Y lo/hi | X speed | Y speed | X frac | Y frac | other | |---|---|---|---|---|---|---|---|---|---| | bounce | 4 | $1699 | $16A5/$16AD | $16A1/$16A9 | $16B5 | $16B1 | $16B9 | $16BD | $16C9 direction (bits 0-1), $1901 properties | | score | 6 | $16E1 | $16ED/$16F3 | $16E7/$16F9 | — | $16FF | — | — | $1705 layer | | smoke | 4 | $17C0 | $17C8/— | $17C4/— | — | — | — | — | $17CC timer | | spinning coin | 4 | $17D0 | $17E0/$17EC | $17D4/$17E8 | — | $17D8 | — | $17DC | $17E4 layer | | minor extended | 12 | $17F0 | $1808/$18EA | $17FC/$1814 | $182C | $1820 | $1844 | $1838 | $1850 timer | | cluster | 20 | $1892 | $1E16/$1E3E | $1E02/$1E2A | — | — | — | — | | | extended | 8 (+2 fireball) | $170B | $171F/$1733 | $1715/$1729 | $1747 | $173D | $175B | $1751 | |

The bounce fractions: PIXI's names put the X fraction at $16B9 and the Y fraction at $16BD. SMW's own bounce code uses them the other way round (see BounceUpdatePos).

  • The 4.4 position update U(s, f, p), used by several routines. s = 8-bit speed (signed, 1/16 px per frame), f = the 8-bit fraction byte, p = the 16-bit position (two bytes):
    1. f ← (f + ((s & $0F) << 4)) mod 256; c = 1 if that sum was ≥ 256.
    2. p ← (p + q + c) mod $10000, where q = floor(sext8(s) / 16) (a value −8..7) as 16 bits.
    3. On exit: Y = $00 if s < $80, else $FF. A = the new high byte of p. N, Z, V and C are those of the high-byte add (hi(q) + hi(p) + carry from the low byte); C = carry out of the 16-bit sum.

This is exactly SMW's $02B526 (bounce Y), $02B560 (extended Y) and $02B58E (spinning coin Y).

  • The spawn routines take the number in B, not A. Every Spawn/*Generic routine stores the high byte of the accumulator (B) as the new sprite's number; the low byte of A on entry is ignored. The callers' macros in every _header.asm do XBA and then fill $04-$07 with their own position, so the number travels in B. A reimplementation must take it from B.

BounceGetDrawInfo

Finds the OAM slot and screen position of bounce sprite X. Handles the X high bit and layer 2.

  • Called with: 8/8, X = bounce slot (0..3). DB must map WRAM (the camera is read absolute, $001A+i).
  • Behaviour:
    1. $03 = $02 (16×16 size bit).
    2. Camera: layer 1 (camX = $1A/$1B, camY = $1C/$1D, i = 0) when $1901,x bit 7 is clear; layer 2 ($1E/$1F, $20/$21, i = 4) when it is set.
    3. $00 = low byte of X16 − camX. If the high byte of the 16-bit X16 − camX is non-zero, $03 = $03 (size bit plus X high bit). The sprite is not rejected for being off screen horizontally.
    4. $01 = low byte of Y16 − camY. hy = high byte of the 16-bit Y16 − camY.
  • Returns:
    • hy ≠ 0 (not drawable): C=0, A = hy, Z=0, N = bit 7 of hy, Y = i (0 or 4).
    • hy = 0: C=1, Y = A = SMW's OAM index byte at $0291ED + x ($10,$14,$18,$1C), N=0, Z=0.
    • X preserved. $00, $01 and $03 are written on both paths; $02 and $04-$0F are untouched.
  • Equivalent SMW code: the bounce-sprite draw prologue $0291F8-$02922D, same OAM table. Differences:
    • SMW takes the layer from $16C9,x bit 7; PIXI from $1901,x bit 7.
    • SMW rejects the sprite when the X high byte is non-zero; PIXI keeps it and sets the X high bit in $03.
    • SMW leaves the camera bytes in $02-$05; PIXI writes only $00, $01, $03.
  • Calls: none.
  • Edge cases: X ≥ 4 reads past SMW's 4-byte OAM table (into code at $0291F1).

BounceGenericDraw

Draws bounce sprite X as one 16×16 tile.

  • Called with: 8/8, X = bounce slot, A = tile number. DB must map WRAM.
  • Behaviour: $02 = A. Then BounceGetDrawInfo. If that reports C=0, return at once with its exit state ($02 = tile is the only extra write). Otherwise, with o = the OAM index it returned:
    • $0200+o = $00, $0201+o = $01, $0202+o = $02.
    • $0203+o = $1901,x ORed with the byte at direct page $64 (SMW's sprite priority), not with the value $64 [MEASURED]. With RAM cleared it is $1901,x exactly.
    • $0420 + o/4 = $03.
  • Returns:
    • Drawn: Y = o/4, A = $03 ($02 or $03), N=0, Z=0, C=0. The routine gives no draw status: C is 0 on both paths (for slots 0..3).
    • Not drawn: BounceGetDrawInfo's C=0 exit.
    • X preserved.
  • Equivalent SMW code: the rest of SMW's bounce draw from $02922D writes the same OAM bytes (position, tile, $1901,x | $64, size into $0420) with SMW's own tile choice and off-screen rule.
  • Calls: BounceGetDrawInfo.

Changes to the 1.2.x routines in 1.40

The 1.2.x files were compared with the 1.40 files of the same macro name (ExtendedX → Extended/X.asm, SpawnX → Spawn/X.asm), both reduced to their instructions (comments, label spelling and 1.40's local-label syntax removed, defines resolved). The two sa1def.asm files give the same values for every define these routines use.

Changed in behaviour: 1 of 27 (ExtendedGetDrawInfo).

ExtendedGetDrawInfo: changed

  • Vertical rule. The 1.2.x rule (t formed by addition) is gone. 1.40 uses the true high byte of the 16-bit Y16 − camY16. With d = (Ylo − camYlo) mod 256 and h = that high byte:
    • h = 0: erase if d ≥ $F0, otherwise visible.
    • h = $FF (up to one screen above): erase if d < $C0; hide ($02 = $F0, not erased) if d < $E0; otherwise visible.
    • any other h: erase, with C = 0 [MEASURED].

Registers on return keep the same shape: visible with h = 0: A = d, C=0; visible with h = $FF: A = d, C=1; hidden or erased: A = $F0, N=1, Z=0. The X-axis rule, $00, $01 and the erase ($170B,x = 0) are unchanged.

  • OAM index table. 1.40 reads SMW's $02A153 directly instead of its own copy. Slots 0..7 get the same values. Slots 8 and 9 now get SMW's next bytes, $2C and $2D (defined, but not usable OAM indexes), instead of whatever followed PIXI's copy. Callers still must not use those slots.

Same behaviour, different code

  • Star: the player-side test is now a JSL to the shared SubHorzPos instead of a private copy reached by JSR. Same writes ($0E-$0F, Y) and results; it uses one more byte of stack, and a 1.40 Star needs SubHorzPos inserted too.
  • SpawnExtended: the search start is written as !ExtendedSize − 1, which is 7, as before.
  • ExtendedHurt: the bank-2 RTL address is written as $B888 instead of $B889 − 1. Same value.
  • ChangeMap16, GetMap16, SubOffScreen, Aiming: the !EXLEVEL / !SA1 conditionals are written as comparisons. Both defines are only ever 0 or 1, so the same branch is assembled.

Identical

Aiming, CapeContact, ChangeMap16, CheckForContactAlternate, CircleX, CircleY, ExtendedCapeClipping, ExtendedHurt, ExtendedSpeed, FinishOAMWrite, FireballContact, GetDrawInfo, GetMap16, LoseYoshi, Random, SetPlayerClippingAlternate, SetSpriteClippingAlternate, ShooterMain, SpawnExtended, SpawnSmoke, SpawnSprite, SpawnSpriteSafe, Star, SubHorzPos, SubOffScreen and SubVertPos behave the same (only labels, comments, layout and the spellings noted above differ). sa1def.asm macros

Interface contracts for the assembler macros PIXI defines in asm/sa1def.asm, the file every PIXI sprite is assembled with. Same rules as the routines: behaviour only. The 1.2.x-era copy has 7 macros and first includes an optional config.asm; the 1.40 copy has the same 7 plus invoke_sa1, and no config.asm include.

Defines the macros depend on

  • !SA1: 1 when the ROM header byte $00FFD5 is $23 (SA-1 map mode), else 0. Set by sa1def.asm.
  • !Base2: $6000 on SA-1, $0000 on LoROM. Set by sa1def.asm.
  • !extra_bits: the extra-bits sprite table, indexed by slot: $7FAB10 (LoROM) / $6040 (SA-1). Set by sa1def.asm through define_sprite_table.
  • !__debug: optional, from the user or the command line; treated as 0 when undefined.

debugmsg(msg)

  • Purpose. Assembly-time trace: tells the user where a piece of code landed.
  • Effect. Emits no bytes. If !__debug is undefined it becomes defined as 0. When !__debug equals 1, the assembler prints a line made of $, the current PC in hex, a space and the text msg. Otherwise nothing is printed.
  • Registers/RAM. None (no code generated).
  • SA-1. Identical.

BES(label): branch if extra bit set

  • Precondition. M=1 (8-bit A); X = the sprite's slot. On SA-1 the table operand is the absolute $6040,x, so DB must reach I-RAM/BW-RAM there ($00-$3F/$80-$BF); on LoROM it is the long $7FAB10,x and DB does not matter.
  • Effect. Tests bit 2 (value $04) of the sprite's extra-bits byte !extra_bits,x, the "extra bit" Lunar Magic stores per placed sprite. Branches to label when the bit is set, falls through when clear.
  • Leaves. A = $04 when the branch is taken, $00 when it falls through; B, X, Y unchanged. Z clear when taken, set when not; N clear; C and V unchanged. No RAM written.
  • Limits. Short relative branch (±128 bytes): label must be near.
  • SA-1. Same, with the table at $6040,x.

BEC(label): branch if extra bit clear

  • Exactly as BES with the sense inverted: branches to label when bit 2 of !extra_bits,x is clear (A = $00, Z set), falls through when it is set (A = $04, Z clear).

Between(x, label)

  • Parameters. x is an operand written as it would follow an instruction, normally an immediate such as #$10. The macro also needs "two times x", which the assembler forms by appending *2 to that text (so #$10 gives the immediate $20). label is a near (short-branch) label.
  • Effect. Signed range check on A: falls through when -x <= A < x, branches to label otherwise. In effect: A + x (carry cleared first) is compared, unsigned, with 2*x; the branch is taken when the sum is greater than or equal.
  • Leaves. A = original A + x, wrapped to the register width: A is modified. C set when the branch is taken, clear when it falls through; N and Z from the comparison; V from the addition. X, Y and RAM untouched.
  • Width. Works in whichever width M selects. With an 8-bit A, 2*x must fit in a byte (x ≤ $7F).
  • SA-1. Identical.

invoke_snes(addr)

  • Purpose. Run from SA-1 code to make the SNES CPU execute a routine (work the SA-1 cannot do, such as touching PPU or DMA registers). Relies on the SA-1 Pack (1.10+) SNES-side IRQ handler.
  • Parameters. addr: 24-bit address of a routine for the SNES CPU, ending in RTL.
  • Effect. Stores addr little-endian at $0183 (low), $0184 (high), $0185 (bank); writes $D0 to SA-1 register $2209 (raises the SA-1-to-SNES IRQ with the custom IRQ vector selected); waits until $018A reads non-zero (the SA-1 Pack's handler sets it once the SNES routine has returned); then stores 0 to $018A.
  • Leaves. Assumes M=1. A clobbered; X, Y unchanged; Z set, N clear at exit. RAM $0183-$0185 = addr, $018A = 0.
  • LoROM. Meaningless: on a non-SA-1 ROM it hangs, since nothing sets $018A. Only assemble it inside if !SA1 blocks.

invoke_sa1(label), 1.40 only

  • The SNES-side counterpart: makes the SA-1 CPU run label (ending in RTL; DB is not set for it, so it must set its own). Stores the 24-bit label at $3180 (low), $3181 (high), $3182 (bank), then calls, with a near JSR, the SA-1 Pack's call-SA-1 helper at $1E80, which returns once the SA-1 routine has finished. The calling code must run in a bank where $1E80 is that helper ($00-$3F/$80-$BF). Assumes M=1; A clobbered. SA-1 only.

define_sprite_table(name, addr, addr_sa1)

  • Effect. Assembly time only, no bytes: defines !name as addr when !SA1 is 0 and as addr_sa1 when !SA1 is 1. name is used as text: it may be passed quoted and may start with a digit (sa1def.asm itself defines both !7FAB10 and !extra_bits this way, each resolving to $7FAB10 / $6040).
  • Note. !SA1 must be set before it is called. Calling it again for an existing name overwrites it.

define_base2_address(name, addr)

  • Effect. Assembly time only: defines !name as addr when !SA1 is 0, and as addr OR !Base2 (addr | $6000) when !SA1 is 1. Meant for $0100-$1FFF WRAM addresses that the SA-1 build relocates to $6100-$7FFF.
