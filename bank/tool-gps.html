the format and CLI docsREADME.txt, Changes.txt
  • A block is reached through Lunar Magic's contact handlers. GPS writes twelve identical 16-byte stubs over $06F690…$06F7E0 (Below, Above, Side, SpriteV, SpriteH, WallFeet, WallBody, …). Each stub loads id*3+1 — the byte offset of that contact type's JMP in the block header, because db $42 is followed by three-byte JMPs — and JSL block_execute.
  • block_execute checks block_bank_byte (0 = not inserted), pulls a 16-bit pointer from block_pointers_1, or block_pointers_2-$8000 for ids ≥ $4000 where the already-shifted negative X is the range test, adds the contact offset, LDX $15E9, then JML [$0000|!dp].
  • db $37 is the wall-run header. Contact offsets ≥ #$001E (WallFeet/WallBody) are only honoured when the block's first byte reads $37 — that byte is the entire opt-in mechanism. Two extra hijacks support it: WallRun at $06F67B and FixSpriteH at $06F717.
  • SA-1 is resolved at assembly time, same trick as UberASM: read1($00FFD5)==$23 detects SA-1 and $00FFD7==$0D picks fullsa1rom over sa1rom, flipping !dp $0000→$3000, !addr $0000→$6000, !bank $800000→$000000, !sprite_slots $0C→$16. The define_sprite_table macro emits two aliases per table (!sprite_status and !14C8), which is why routines can be written with raw vanilla addresses and still be SA-1 correct.
  • Block positions live in $98-$99 (Y) and $9A-$9B (X), level space, and $1933 is the layer being processed. $5B bit 0 (vertical level) is why get_map16/change_map16 swap $99/$9B internally — and why a swap_XY routine exists purely to undo it. Worth knowing before trusting either convention.
  • -O2 is a documented crash risk: it truncates the bank-byte table, so undefined block IDs end up with no bank byte and will crash if Mario touches them. -O2 also silently implies -O1 (not in the README). -O3 parses but errors as unimplemented.
  • Block IDs run 0x200-0x7FFF, acts-like must be < 0x8000 — bounds the README only implies. The shipped list.txt is empty apart from a comment.
  • GPS finds its own data in an already-patched ROM via a "GPS_VeRsIoN" marker embedding the table addresses and sizes. It can also detect and strip BTSD (string-scans for "Blocktool Super Deluxe"), but only hack version $3136.
  • README is out of date in one spot: -nw was added in V1.4.5 and appears in the tool's own -h output but not the README. Flagged AMBIGUOUS in the graph.
  • Sharp edges found in the routine library, all flagged in the graph: $185E is overloaded across three routines; move_spawn_above_block does TAX with no PHX and so clobbers the caller's X, unlike all four of its siblings; rainbow_shatter_block differs from shatter_block by exactly one omitted LDA #$00.

Custom blocks: bringing GPS into Pipe Dream

Plan for doing Gopher Popcorn Stew's job (GPS V1.4.5, custom block insertion) inside Pipe Dream, without shelling out to gps.exe. Started 2026-10-10. Background on GPS's on-ROM format is in ROM_TOOLING.md § "GPS — what to look at"; this file is the plan, not the reference.

What GPS does, which is what we have to do

  1. Read list.txt: Map16 tile (or range) → block .asm, optional acts-like.
  2. Assemble each block with Asar. A block is db $42 (or db $37 for wall-run) followed by three-byte JMPs, one per contact: Mario below/above/side, sprite V/H, cape, fireball, top corner, body inside, head inside (+ wall feet/body for $37).
  3. Put each routine from routines/ that a block calls (%name()) into freespace once, and give the blocks a macro that JSLs it.
  4. Write the per-tile tables (block_bank_byte, block_pointers_1/_2) and the twelve contact stubs at $06F690-$06F7E0 that JSL block_execute; main.asm is that driver.
  5. Set each tile's acts-like.
  6. On re-insertion, find the previous run (the "GPS_VeRsIoN" marker) and free what it claimed (RATS / autoclean) before claiming again.

What Pipe Dream already has

  • RatsWriter: RATS enumeration and allocation in the expanded area. Asar's freespace speaks the same protocol, so the two can share a ROM — but the order they run in at build matters.
  • Acts-like: RomPrep owns a table at $11:8000 and detects Lunar Magic's acts-like hook; RomBuilder.ReplayMap16 writes the project's acts-as edits into LM's table at build.
  • Projects apply their edits at build (RomBuilder), onto a pinned base ROM. Blocks fit that model: imported into the project, inserted at build, never patched into the base.
  • Asm: a clean-room 65816 emitter for RomPrep's own code. Not a substitute for Asar here.

Phases

Each phase ends shippable. The Asar ones waited on the licence, settled 2026-10-17 (open question 2).

1. Read GPS blocks off a ROM — no assembler

  • rom/GpsBlocks.cs (storage): find GPS in a ROM — the "GPS_VeRsIoN" marker, cross-checked by following the $06F690 stub's JSL into block_execute and reading its table operands, the way LunarMagic.cs reads LM's hooks. Per Map16 tile $200-$7FFF: inserted or not, the block's SNES address, its header ($42/$37), and which contacts do something (a JMP whose target is a bare RTL handles nothing).
  • Session gateway + UI: the Map16 editor's tile readout says "custom block" with its address, header and handled contacts, beside the acts-like it already shows; a badge on custom tiles in the Map16 sheet.
  • Exit: on a GPS-patched ROM, every tile gps.exe inserted is reported with the right address (checked against a list.txt we inserted ourselves with gps.exe), and nothing else is.
  • Status (2026-10-10): rom/GpsBlocks.cs reads the marker the way gps.exe's clean_hack does (asm version 1 without the pages-40+ byte, 2+ with it, both pointer tables), but only behind the $06F690 stub's JSL target. The Map16 editor shows a corner tag on custom tiles, "GPS $addr" in the gutter, the block in the hover card and on the selected tile's label. GpsBlocksTests covers it on a synthetic ROM.
  • First real hack (What The Shell 2!!, BPS on vanilla): asm version 3, pages-40+ layout, 965 blocks over 229 code addresses, headers and JMP tables disassemble as read. 606 of them sit on LM's FG pages 40-7F and 35 more past the old flat tile count (0xFB0), so at first the editor showed 324. Fixed by the Map16 work of 2026-10-12 (CONTRACT §7a-rev, §9d): tiles are numbered as LM numbers them (BG 0x8000+), exist per range, object 0x29 places pages 40-7F on layer 1, and their acts-like is LM's second table. All 965 now show, with their acts-like.
  • Oracle check (2026-10-13): passed. GPS built from its own src.zip on the Mac (see "The local oracle" below) re-inserted a copy of What The Shell 2!! with this list:

200:0130 above.asm ; $42, Mario above only, calls %glitter() 2FF wall.asm ; $37, wall feet + wall body only R203-214:0025 none.asm ; template.asm: every contact a bare RTL 4005:0130 above.asm ; pages 40+

GpsBlocks.Read then reported exactly 7 blocks (200, 203, 204, 213, 214, 2FF, 4005) and none of the 965 GPS had just cleaned out: headers, handled contacts and acts-like as listed, one address for the two uses of above.asm and one for the four of none.asm, and 2FF kept the hack's own acts-like (04C) since its line sets none. Not a checked-in test: the ROM is derived from SMW and a third-party hack, and the oracle needs a native build CI doesn't have.

2. Asar in the build

  • Build Asar's shared library from the pinned source (~/asar, 5fd539c, API 3.3.0) for win-x64 and linux-x64 in CI; a local libasar.dylib keeps the Mac dev loop working (Mac stays unshipped). Vendor asar.cs; wrap it in one storage-layer class.
  • Asar's state is process-global: one patch at a time, behind a lock, like SpriteRender.Capture.
  • Exit: a test patches a small .asm onto an in-memory ROM and checks the bytes and the RATS tag; ROM-less CI still passes (the test skips without the native library, as ROM tests skip now).
  • Status (2026-10-13): data/Asar.cs binds the seven calls a patch needs (apiversion, init, patch_ex, errors, warnings, prints, written blocks) straight from asardll.h's documented structs, instead of vendoring asar.cs (that file is LGPL; only the C interface files carry the WTFPL exception). One lock; PIPEDREAM_ASAR points it at a dev build, else the library is looked for beside the app. AsarTests pass against the local libasar.dylib and skip without it. Since 2026-10-16 CI builds it for win-x64 and linux-x64 with tools/asar/build.sh, runs these tests against it, and publishes it packed inside the app (the AsarLib item in the csproj); --asarcheck on the published binary and on the installed Windows app proves the packed copy loads. PIPEDREAM_ASAR still overrides it.
  • Speed (2026-10-13): a patch on a 4MB ROM took 13.7 ms, 77% of it a CRC Asar takes over the whole ROM after every patch for the symbols file alone. Taking that CRC only when a symbols file is asked for: 2.3 ms.
  • Quasar (2026-10-14): our fork of Asar, [john-sparwasser/quasar](https://github.com/john-sparwasser/quasar), branch quasar, where the speed work lives (the lazy CRC is its first commit). It keeps Asar's API and library name, so it drops in where Asar would and stays replaceable. Under the LGPL it is a modified Asar: its README says so, Alcaro stays credited, and the public fork is the source we offer, so it must stay up and its pinned commits reachable while a release ships them. tools/asar/build.sh builds the pinned commit; QUASAR_SRC=<checkout> builds a working tree. Not offered upstream.

3. Insert blocks from a GPS folder

  • Import copies blocks/, routines/ and the user's main.asm/defines.asm into the project folder, and list.txt into the project file (the decision above). Running their driver through Asar keeps exact compatibility, and means we ship none of GPS's assembly.
  • C# does what gps.exe does around it: read the project's blocks, generate the routine macros, assemble each block, fill the tables, write the marker, clean up the last insertion.
  • Build order with Pipe Dream's own allocations is decided here, once.
  • Exit: the same inputs built by Pipe Dream and by GPS give equivalent tables and block code (the local oracle below; compare extracted tables, not whole ROMs).
  • Status (2026-10-13): the inserter, not yet the import or the build. data/GpsInsert.cs does gps.exe's job in one Asar patch where gps.exe runs one per block file: clean the last insertion, the user's main.asm (tables as in-memory placeholders, filled in after the patch from the blocks' labels), routine macros, then each distinct block in freecode and its own namespace. Asar frees autocleaned space in pass 0, so the new insertion reuses the old. On What The Shell 2!! with the oracle list: every tile's header, handled contacts and acts-like, and every block's code (JMPs taken relative, JSLs followed), match gps.exe's output; gps.exe re-inserts cleanly over ours; ours over ours twice claims the same RATS bytes. 27 ms warm, including cleaning out the hack's 965 old blocks; per block, as gps.exe does it, that hack's 229 files would be ~3 s. GpsInsertTests run it through a minimal driver of our own (GPS's files have no licence). Differences from gps.exe, all from sharing one patch: two block files defining the same macro collide, and a define set by one block is visible to later ones. Not done: no .dsc, no -O1/-O2, no BTSD removal; import into a project and running it at build.
  • Import (2026-10-14, reshaped 2026-10-15): GpsInsert.Import copies main.asm, defines.asm, blocks/ and routines/ into <project>/gps/ (Debug ▸ Import GPS folder…) and hands list.txt back parsed; the session puts each tile's block into ProjectFile.Blocks (tile hex → file under gps/blocks/, ranges and rectangles expanded, a later line's tile wins) and each acts-like the list gives through the Map16 editor's SetActsAs, so it lands in the live ROM and in Map16.ActsAs like any other acts-as edit, one undo step per value. list.txt itself is not copied. The import checks list.txt parses and every listed block exists, and stages the copy before swapping it in, so a bad folder keeps the last import and hands over no list. The assembly sits beside project.pdp, not in it, so blocks stay editable in the user's editor; sharing a project with blocks means sharing gps/ too. Superseded 2026-10-16: the import now reads the folder into the .pdp — driver and routines into GpsFiles (replacing the last import's), blocks/*.asm into BlockLibrary (merged by name), list.txt over Blocks — and a project with the old gps/ folder has it read in on open (Project.Open; the folder is left on disk). The real GPS 1.4.5 folder inserted onto What The Shell 2!! this way is byte-identical to the folder-based inserter's output.
  • Build (2026-10-14): RomBuilder.Build inserts the project's blocks first, before ReplayMap16, so the old insertion's space is freed before Pipe Dream allocates. The inserter puts the acts-like tables back as the ROM has them and ReplayMap16 then writes the project's acts-as, block tiles included: one owner. An Asar error fails the build with file:line: message; no library skips the blocks with a warning. ~17 ms on What The Shell 2!! with the oracle list. A prepped base takes blocks from prep v30, which carries LM's custom-block dispatch (CONTRACT §PREP V30): through v29 the stubs GPS writes at $06F690 had nothing calling them, and prep's acts-like remap read $11:8000, not the table GPS repoints $06F624 to. An older prepped base fails the build with "upgrade base". Mesen (2026-10-14, macOS, tools/mesen/probe.sh): a block (acts like $130) in a column in level $105 fires when Mario walks into it on v30, 3/3 runs, and never on the same build at v29; level $105 plays the same on plain v29 and v30 (Mario position, death spot, timer, frame counter). Prep v31 (2026-10-16) restamps the marker and the fourth trampoline as LM 3.40 writes them, so its Map16 save leaves the dispatch alone (CONTRACT §PREP V31); the block fires 3/3 on a v31-stamped build too.
  • Saved in Lunar Magic (2026-10-15, Windows, LM 3.40, GPS 1.4.1's main.asm from the user's own hack): a v30 project with two blocks (one acts-like $130 that sets lives to 99 on any Mario contact, placed as a 3-tile column in level $105) was built, then copies went through LM's level save (Ctrl+S, dirtied), the 16x16 editor's F9, -ImportLevel and -ImportAllMap16 (tools/lm/Invoke-LmGui.ps1 drives the two GUI routes). The block fires 3/3 before and after every one of them. Nothing LM wrote touches GPS's bytes: the stubs in $06F690+, its two JML hijacks at $06F67B/$06F717, its marker, tables and block code are byte-identical through all four saves, and the four acts-like sites still JSL to LM's trampolines. What the two Map16 routes (F9 and -ImportAllMap16, identical diffs) DO write is LM upgrading the dispatch it finds: the marker goes LM 11 01 → LM 12 01 and the fourth trampoline at $06F7A0 is rewritten to LM 3.40's 20-byte shape (17 bytes differ from What The Shell 2!!'s, whose LM was older); $06F626 goes $91 → $11 (GPS's FastROM-mirrored table pointer, normalised to the same table); and LM installed its own extended-def ranges and freed our $128000 block — which it also does on a v29 base, and to a plain v30 or v29 base on an F9 with no edits at all (LM_PARITY §2 "Map16 F9 on a plain v30 base"), so that is 3.40's Map16 install, the known "upgrade offered" state (CONTRACT §PREP V26), not v30's doing and not the page-2 tiles in the file. Hand-stamping the v12 marker and trampoline first makes the same import leave $06F65C-$06F7EF entirely alone, and that ROM plays the same (see CONTRACT §PREP V30 for the follow-up this suggests). The level save writes 8 runs, none near the dispatch.

6. ROMs that already carry GPS blocks

  • A base ROM inserted with gps.exe before it came to Pipe Dream: phase 1 reads it; phase 3 must free the old insertion (or adopt it) before claiming its own. Decide which, with real hacks.
  • Decided (2026-10-16): refuse until the GPS folder is imported. The local oracle: GPS and Asar built on the Mac

No Windows PC needed. main.cpp is portable (its Asar loader dlopens ./libasar.dylib), it expects Asar API 303, and the pinned ~/asar (5fd539c, v1.91+16) is API 3.3. Built in a scratch dir, never in the repo (GPS has no licence):

cmake ~/asar/src -DCMAKE_BUILD_TYPE=Release -DASAR_GEN_EXE=OFF -DASAR_GEN_DLL=ON \
      -DASAR_GEN_LIB=OFF -DASAR_GEN_EXE_TEST=OFF -DASAR_GEN_DLL_TEST=OFF && cmake --build . -j8
clang -c asar/asardll.c && clang++ -std=c++17 main.cpp asardll.o -o gps     # from src.zip

GPS works in the current directory: copy main.asm, defines.asm, routines/, a blocks/ and list.txt beside gps and libasar.dylib, then ./gps rom.sfc. It refuses a ROM Lunar Magic has not saved (it reads LM's acts-like pointer at $06F624), so vanilla will not do, and pages 40+ need LM to have created them ($06F63C != FF). main.cpp is dated the day before the shipped gps.exe; one byte-compare against gps.exe on Windows would confirm the build matches, but nothing waits on it.
